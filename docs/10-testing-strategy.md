# 10 — Testing Strategy

pytest in `backend/hb/tests/`. Test DB = fresh SQLite file per test via `tmp_path` fixture + alembic upgrade (or `metadata.create_all` for speed; one smoke test runs real migrations). External HTTP is **never** hit in tests: every outbound call sits behind a thin seam that tests monkeypatch with data built inline in the test — there are no recorded JSON fixtures; the only files under `tests/fixtures/` are the synthetic Census extracts in `tests/fixtures/census/` (§3) and `geography_tx_minimal.toml`. The seams: `listing_scan.fetch_homeharvest` / `fetch_photo`, `backfill_sales.fetch_sold`, `enrich.fetch_realtor_estimate` / `fetch_rentcast_avm` / `fetch_photo` (plus `realtor_gql.post` / `resolve_mpr_id` and `httpx.get` for the RentCast and Zestimate unit tests), `price_history.fetch_price_history`, `fred.fetch_observations`, `redfin_market.fetch_signature` and `JobRunner.download_to_raw` (also `zillow_research`), `hazards_fetch.fetch_layer`, `schools.fetch_schools`, `school_districts.fetch_districts`, `school_ratings.fetch_caaspp`, `schooldigger.fetch_district_page`, the open-house sources' `realtor.fetch_properties` / `redfin.fetch_gis` (stubbed for every test by `conftest.py`, because `listing-scan`'s tail runs that job), `geocode.fetch_census`, `channels._pushover_post` / `send_toast`, `schedule_install.run` and `setup_geo.fetch_reference`; `time.sleep` is patched out wherever a job paces itself. Inline fixture people, phones, emails and addresses are fictional (`example.com`, `555-01xx`). Every test runs against the packaged `sf_peninsula` geography: `conftest.py` pins `settings._geo` (autouse) so a developer's `geography.toml` never leaks in, and `set_geography()` narrows the city list per test. `tests/fixtures/geography_tx_minimal.toml` (Travis County, TX) is loaded by the tests that exercise the `us` pack and the state-parameterised pipelines. `test_packs.py` validates every registered pack (`hb.packs.validate`) and asserts the `us` base carries no California wording; `test_migrations.py` asserts the six migrations, applied in order, match `models.py`.

## 1. Layers
1. **Unit** — engine math (CMA scoring, adjustments, overbid quantiles/shrinkage, affordability, offer bisection), resolve cascade, relist stitcher, dedup keys. Pure functions preferred; most tests need no DB.
2. **Pipeline integration** — run a pipeline against fixture data into a real (temp) SQLite DB; assert row counts, upsert keys, events, run logs.
3. **API** — FastAPI TestClient over a seeded DB; response shapes match `07-api-spec.md`.
4. **Golden backtest** — the credibility test for the whole product (§4).

## 3. Engine unit-test anchors
- CMA: the worked example in `06-algorithms.md` §4.3 is a literal test case (assert $2,198,766 ±$1); bracketing swap logic; relaxation ladder order; confidence rules table.
- Overbid: worked example 06 §5.5 (assert p50_final = 1.106 ±0.001); fresh/stale routing (price-cut subject → stale); shrinkage limits (n_eff=0 ⇒ city distribution; huge n ⇒ ZIP distribution).
- Affordability: 06 §8 example (PITI $13,721 ±$1); PMI drop at exactly 20%; reserves warning boundary.
- Offer solver: binding-constraint selection; bisection convergence; gap cap behavior (bid above E + tolerance ⇒ infeasible region).
- Time index: interpolation for missing months; carry-forward flag past series end.
- `hb setup` (`test_setup_geo.py`): tiny synthetic Census files in the real formats under `tests/fixtures/census/` stand in for `setup_geo.fetch_reference`. Anchors: an incorporated city beats a same-named CDP; a ZIP shared by two chosen cities goes to the larger share; a city with no majority ZIP keeps its largest free one; county = most of the city's land; tax rate = ACS taxes ÷ value, the state's ratio when a county is suppressed, the pack's `purchase_tax_rate` when set; the rendered file passes `geography.parse`; an existing `geography.toml` is never replaced without a yes.

## 4. Golden backtest (CMA credibility gate)
Script `hb backtest --n 20`: select ≥ 20 `sales` from the last 60 days in target ZIPs with sufficient prior data; for each, run the CMA and overbid model **as of the day before its list date** (filter all inputs by date — no leakage: comps sold before that date only, index truncated).
Report: median absolute % error of the **blended predicted value** (`valuation.CMA_WEIGHT`·CMA + rest·overbid point — the number the product displays) vs actual sale price; CMA-only MdAPE as a diagnostic line (no threshold); share of actuals inside the overbid **calibrated predicted range** (p25–p75 widened by `overbid.RANGE_WIDEN`, per `06-algorithms.md` §5.4).
**Pass** (PRD success criterion 1): blended MdAPE ≤ 8%; calibrated-range coverage ≥ 50%. Output a markdown report to `data/backtests/<date>.md`; a failing gate makes `hb backtest` exit non-zero and means the parameters (half-lives, m factor, k, blend weight) need tuning — tuning knobs and chosen values recorded in that report. All backtest inputs are strictly as-of filtered: comps, price index, the subject's price-cut events, and its cumulative DOM (fresh/stale routing must not see the future).

**Pass B — posture calibration (soft gate).** The same run replays the docs/06 §5.6 posture layer on every sale whose pending transition the scan observed (`MIDFLIGHT_WINDOW_DAYS` = 365; `sale_date − lag` can land inside escrow, so only scan-observed pendings qualify), two ways. The **survival replay** re-scores each sale as-of every `SURVIVAL_RATIOS` exposure point (0.25× … 6× the area median) it passed through before going pending — the population a live chip faces, where a lingering home appears at every point and a hot one at the first few; scoring only at the moment a home is about to sell samples the winners and halves the below-asking odds of fresh listings. It is posture-only (no valuation) and produces: the empirical curve (realized below-asking share and median sold/list per grid ratio), the calibration table (predicted `p_below_list` bucketed at the tier boundaries → n, mean p, realized share, median sold/list), strict per-tier precision (sold < as-of asking), the overpriced split by evidence (relisted / cut / neither), the withdrawal share past `posture.WITHDRAWAL_RATIO` (per campaign, exposure to pending or delisting — a withdrawn attempt that relisted and sold is a sale), and an IRLS re-fit of the knobs on this run's rows through `posture.features` — the same design the shipped `EXPOSURE_LOGIT` / `CUT_LOGIT` / `RELIST_LOGIT` came from — printed next to the shipped values. `calibration_ok` = every bucket with n ≥ 50 within max(±10%, 2 binomial SE) of its realized share, and overpriced medium+high precision ≥ 60% at n ≥ 30; `hb backtest` echoes it, but it is a reported line, not an exit code. The **decision-point replay** evaluates each sale once, as-of `MIDFLIGHT_LAG_DAYS` (7) before pending, with the CMA + overbid blend, to score the market-adjusted value: MdAPE of the adjusted value vs the unadjusted blend vs list-as-of (all rows and the `rejection_weight > 0` subset — adjusted must not be worse there); its tier table is printed as a diagnostic with the caveat that fresh buckets read optimistic there. Both replays run independently of pass-A usability (a long-listed home can be comp-starved at list date yet evaluable mid-flight); the offer-date signal is live-only, so both omit it. First run on this design (2026-10-25, 5,436 survival rows from 1,335 sales): calibration PASS — buckets 0.20–0.35 / 0.40–0.60 / 0.65–0.80 realized 26.5% / 46.8% / 68.2% against mean p 0.275 / 0.468 / 0.691; overpriced medium precision 68.2% (n=1,731); the re-fit landed within 0.04 log-odds of the shipped knobs; adjusted 5.21% vs unadjusted 6.19% (w>0 subset: 3.48% vs 6.08%, list-as-of 3.57%); withdrawal share 24% (n=490).

## 5. Spot-parity checks (manual)
Compare 3 ZIP/week combinations of dashboard metrics against the Redfin Data Center UI values; must match exactly (same file) — discrepancy means a mapping bug in `redfin_market.py`.

## 6. Running the suite
- `make test` → `cd backend && uv run pytest` (`testpaths = ["hb/tests"]` in `backend/pyproject.toml`; a plain `uv run pytest -q` from `backend/` is the same thing). `make lint` → `uv run ruff check .` (line length 100). `make build` → the frontend typecheck + Vite build (`tsc -b && vite build`). All three before calling a change done.
- CI (`.github/workflows/ci.yml`) runs on every push to `main` and every pull request, two jobs on `ubuntu-latest`: **backend** — `uv python install 3.12`, `uv sync --frozen`, `uv run ruff check .`, `uv run pytest -q` (the suite is network-free, so it runs anywhere in ~30 s); **frontend** — Node 20, `npm ci`, `npm run build`.
