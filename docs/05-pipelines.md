# 05 — Pipelines

All ingestion jobs. Each is a Typer CLI command (`hb pipeline <job>`), idempotent, and logged to `pipeline_runs`. Only `DAILY_SEQUENCE` (run by `hb pipeline daily`) and `listing-scan` are scheduled (§2); `hazards-fetch`, `school-ratings`, `price-history`, `derive-sales-history`, `backfill-sales` and `enrich` are standalone commands run by hand — `enrich` (for tracked homes) and `open-houses` also run inside `listing-scan`'s tail (§4.5, §4c).

## 1. Platform-wide idempotency & dedup contract (binding)

Every pipeline MUST satisfy:

1. **Re-run safety**: running the job twice in a row produces **zero new rows and zero new events** on the second run. Enforced by: natural-unique-key UPSERTs (`04-data-model.md`), diff-only event emission (§4.4), and content-hash no-ops (§1.1). This is tested per job (`10-testing-strategy.md` §2).
2. **Content-hash no-op** (bulk downloads): raw file saved to `data/raw/<source>/<YYYY-MM-DD>/`; compute sha256; if it equals the last successful run's `pipeline_runs.content_hash` for that job, record status=`noop` and stop. This is what makes daily scheduling of weekly/monthly upstream sources free. `redfin-market` hashes the S3 objects' ETag/Last-Modified/size from a HEAD request instead, so an unchanged week costs no download at all (the files are ~5.5 GB). Jobs that filter the download to the target geography (`redfin-market`, `zillow-research`) also fold the geography's ZIP and city lists into the hash (`geo_fingerprint()` in `pipelines/base.py`), so adding a ZIP or city reloads the unchanged release on the next run instead of leaving the new geo empty until upstream republishes. Dated folders are kept `RAW_KEEP_DAYS` days (§2).
3. **Partial-failure tolerance**: per-item (per-city, per-ZIP, per-property) try/except; count failures; status=`partial` if some items failed, `failed` only if all did. When the last two finished `listing-scan` runs are both `failed`, `hb alerts send` raises a `scan_failure` alert (09 §2).
4. **One run log per invocation** in `pipeline_runs` with counts (`items_seen`, `items_upserted`, `events_emitted`).
5. **No deletes** except the documented truncate-and-replace paths (Zillow price_index rows; derived `build-index` blend rows; `redfin-market`'s `source='redfin'` rows per geo level, §3.1; `market-supply`'s own rows for today, §3.5) and `open-houses`' cancellation sweep, which deletes **future** slots no source reported this run (§4c step 4).

`pipelines/base.py` provides the shared runner implementing 1–4 (context manager: run-log start/finish, hash check helper, per-item error collector).

## 2. Schedule

| Slot (local) | Command | Jobs |
|---|---|---|
| `DAILY_TIMES` (04:00) | `hb pipeline daily --catch-up` | `redfin-market` → `zillow-research` → `fred` → `build-index` → `market-supply` → `hazards` → `schools` → `school-districts` → `schooldigger-ratings` → `deal-deadlines` (sequential; the download jobs no-op via content hash if upstream unchanged — Redfin updates weekly, Zillow monthly; the derived jobs always recompute; `schooldigger-ratings` is quota-capped and converges across days; `deal-deadlines` is a pure DB read). The authoritative order is `DAILY_SEQUENCE` in `hb/pipelines/__init__.py`. |
| `SCAN_TIMES` (05:00, 15:00) | `hb pipeline listing-scan --catch-up` | the scrape (§4), then `open-houses` (§4c) in its tail — twice a day, so a home listed in the morning and its weekend open houses show the same afternoon |
| hourly :30 | `hb alerts send` | deliver undelivered alerts (09 §4) |
| once | `hb pipeline hazards-fetch` | download the pack's hazard polygon layers for the geography (§16); `make load` passes `--if-missing` (only layers with no file yet); rerun without it when a state re-releases zones |
| yearly | `hb pipeline school-ratings` | CAASPP test-score ratings (§10; a noop unless the pack declares the `caaspp` rating source — only the `ca` pack does) |

Installed per user by `hb schedule install` (`hb/schedule_install.py`; `make start` runs it after `make load`, and `make schedule` / `make schedule-remove` by hand): Task Scheduler jobs through `ops/windows-tasks.ps1` on Windows, launchd agents `com.home-buying.{daily,scan,alerts}` in `~/Library/LaunchAgents` on macOS (`StartCalendarInterval` on the minute, `RunAtLoad`; a missed interval fires on wake), systemd `--user` timers `hb-{daily,scan,alerts}.timer` in `~/.config/systemd/user` on Linux (`OnCalendar` hourly, `Persistent=true`, `OnStartupSec=10min`) or, with no systemd user instance, a block between `# >>> home-buying schedule` markers in the user's crontab (`ops/crontab.txt` is the same three lines as a template). All as the user, no administrator; launchd, systemd and cron write output to `DATA_DIR/logs/hb-<job>.log` (the Windows tasks run headless and keep no log file); every call out goes through the `run()` seam the tests stub. The home server uses the system-level timers in `ops/linux/` instead. Besides the OS schedule, `hb serve` runs the same hourly check itself (`hb/scheduler.py`: a daemon thread, first pass 60 s after start, then every hour; `HB_SERVE_SCHEDULER=false` turns it off, which `ops/linux/hb.service` sets since the timers do the work). The two never double up: `needs_run` also treats a `running` row younger than `IN_PROGRESS_GRACE` (3 h) of the job — any job of the daily sequence for `daily` — as served. **The OS scheduler fires every hour** (and 10 min after logon); `--catch-up` (`hb/pipelines/schedule.py`) runs the job only when its latest slot — `SCAN_TIMES` / `DAILY_TIMES`, local wall-clock in the geography's timezone — has no completed run started at or after it, and otherwise prints `up to date, skipping`. "Completed" is `ok|partial|noop` for `listing-scan` (a failed scan is retried next hour) and any finished run of the sequence's last job (`deal-deadlines`) for `daily` (one broken upstream must not re-run the bulk sequence hourly). A slot missed to sleep, a crash, or a run that died before `hb` started is therefore retried within the hour, never silently skipped; `/api/ops/health` reports `scan_overdue_since` once a scan slot is >2 h past without one (07 §Ops, the red header pill in 08).

**Tail of `hb pipeline daily`** (after the sequence, outside any job and its run log): the nightly DB backup to `data/backups/` (11 §2), then raw-cache retention — dated `data/raw/<source>/<YYYY-MM-DD>/` folders older than `RAW_KEEP_DAYS` (default 90; `0` keeps everything) are deleted (`hb/pipelines/raw_cache.py`; `hb prune-raw` runs the same step by hand). Only date-named folders directly under a source are candidates, so undated reference data such as `data/raw/hazards/` (§16) is never touched. `hb setup` caches its Census reference files in dated `data/raw/census/<YYYY-MM-DD>/` folders, so they age out like any download and a later `hb setup` fetches them again. Safe because every release restates upstream history and the loaded rows live in the DB: the no-op check in §1.2 compares `pipeline_runs.content_hash`, not files on disk, so a pruned folder never triggers a re-download. A failure in either step is reported and does not fail the run.

Tasks run `uv run --no-sync hb …`: a syncing `uv run` rewrites `.venv\Scripts\hb.exe`, which the always-on server holds open, so after any `pyproject.toml`/`uv.lock` change every task would exit 2 before `hb` starts. The venv is synced by `make install` and by `make deploy-windows` while the server is stopped (11 §2); on the home server `ops/deploy-server.sh` syncs it under the running service, which Linux does not lock (11 §2b).

## 3. Bulk jobs

### 3.1 `redfin-market`
1. HEAD the `all_zips`, `all_cities`, `all_counties` Data Center CSVs (03 §1.1); sha256 the combined ETag/Last-Modified/size plus the target ZIP/city lists → compare with the last ok/noop run's `content_hash` → `noop` without downloading. Otherwise say how many files and how big (the Content-Length sum from the HEAD signatures, `_total_bytes`; "several GB" when a HEAD gave none), then download all three to the raw cache. `JobRunner.download_to_raw` logs each file's size as it starts, its progress every `PROGRESS_EVERY_BYTES` (512 MiB) and a closing line: the three files are ~5.5 GB, and a first run must not sit silent for the whole download.
2. DuckDB `read_csv` (`all_varchar`, `NA` → NULL): filter `PROPERTY TYPE = 'Single Family Residential'`, `IS SEASONALLY ADJUSTED = false`, `REGION NAME` in the geography's ZIPs / `<city>, <ST>` / its counties (a configured region with zero CSV matches is logged); select the metric columns mapped to the `market_metrics` vocabulary (04), percent columns ÷100; `FREQUENCY` → `period` (`Rolling 3 Months` → `3m`, `Monthly` → `monthly`; any other value raises — fail loudly, never guess a window); per region name keep the `REGION ID` with the most closed sales (namesake dedup).
3. Unpivot to tidy rows; per geo level **DELETE every `source='redfin'` row, then bulk-insert** — Redfin restates history each release and the delete also drops geos that left the target list. A level that matched no target geo is an item failure (never wipe a level with nothing) → status `partial`, its previous rows intact.

### 3.2 `zillow-research`
1. Download ZHVI (SFH ZIP-level) and ZORI CSVs (03 §1.2). Hash-check (file digests plus the target ZIP/city lists) → maybe noop.
2. Filter rows to the geography's ZIPs (+ its cities' rows, matched on `<city>, <ST>`).
3. **DELETE all `price_index` rows with source='zhvi'** for covered geos, then bulk-insert the fresh series (history is restated upstream — never diff). Also UPSERT level values into `market_metrics` as **metric=`zhvi` / metric=`zori`, source='zillow', period='monthly'** — Redfin's `median_sale_price` rows are never overwritten by Zillow data.

### 3.3 `fred`
Fetch `MORTGAGE30US`, `MORTGAGE15US` and, when the geography file sets `[market].case_shiller_fred_id`, that metro Case-Shiller series (stored as `CASESHILLER`) since the last stored date minus 90 days; UPSERT into `rate_snapshots` on `(date, series)`. With no `FRED_API_KEY` the job logs a hint and records `noop` without calling FRED (the key is optional: affordability and offer math fall back to the profile's rate, else 6.5%).

### 3.4 `build-index` (derived)
Purpose: one monthly `price_index` series per target geo for CMA time adjustment (06 §3).
1. For each ZIP: monthly median $/sqft from `market_metrics` (redfin), 3-month centered rolling median.
2. Blend with ZHVI where both exist: `index = 0.5·redfin_ppsf_norm + 0.5·zhvi_norm` (each normalized to its own latest=1.0). Where a ZIP series has months with < 5 underlying sales or gaps, fall back to city series, then county.
3. Truncate-and-replace `price_index` rows with source='blend' for covered geos.

### 3.5 `market-supply` (derived)
Purpose: `months_supply_live`, the now-cast of months of supply from this app's own scan (06 §9, 08 §9), for each trailing window the Supply page can pick. Redfin's published `months_supply` (a rolling 3-month window that closes ~1 month back) arrives at every geo level from `redfin-market`, so nothing is derived from it here. Reads `listings`/`sales`, writes `market_metrics`. No network.

1. **Counts** — active listings now per ZIP, and closed sales per ZIP with `sale_date >= today − W months` for each `W` in `LIVE_WINDOWS` (3, 6, 9, 12 calendar months; `months_ago` walks calendar months, clamping the 31st to a shorter month). Cities roll up through `settings.geo.zip_to_city`, not `properties.city`, so keys are immune to scraper name drift.
2. **Value** — `W * active / sold_W`, `metric='months_supply_live'`, `period=f'{W}m'`, `period_start=today`, `source='derived'`. The window scales the rate, not the stock: the same monthly pace gives the same number under every window; a longer window just smooths it.
3. **Thin-geo fallback** — below `THIN_SALES_THRESHOLD` (10 closed sales in the window; a minimum denominator, so independent of window length) the ratio is noise: a ZIP borrows its city's value (`source='derived_city'`), a thin city emits nothing. (Threshold is higher than `build-index`'s 5: that gates a median $/sqft, this gates a ratio with sales in the denominator.)
4. **Writes**: truncate-and-replace today's rows per window (`metric`, `source IN ('derived','derived_city')`, `period_start=today`, `period`), so the daily history accumulates and published Redfin rows are never touched. The delete also clears a stale row when a geo flips between `derived` and `derived_city` (`source` is part of the unique key).
5. **Backfill** — every morning since the first scan (the day after the earliest `listing_events.observed_at`) that has no rows for a window is replayed and written: active listings as of that morning come from the event log (a listing first seen before the morning, whose status is the `old_value` of its first status event observed on or after it, or its current status if none — `pending | sold | delisted | back_on_market | relisted | status_change` all carry statuses), and closed sales are those dated before the morning within the window, as the `sales` table stands now. Recorded mornings are never overwritten: a stored value is what the app saw that day, a replayed one is the best reconstruction. This is what gives a newly added window its full history at once and lets a missed daily run heal itself.

**Idempotency**: deterministic from its inputs; daily-safe (bounded ~140 new rows/day, like `fred`'s rate snapshots, plus a one-time backfill when a window is new). Live history for every window starts the morning after the first `listing-scan` (2026-07-15); it cannot reach further back because inventory before the first scan was never observed.

## 4. `listing-scan` (the daily scrape)

**Price-band note**: the scan ingests listings and sales at ALL prices — the target price band (`[price_band]` in `geography.toml`) is applied only at alert-matching time (09 §2) and as the default UI filter (08 §2). Filtering ingestion by price would corrupt comps and overbid distributions.

A first scan (`_first_scan`: no `ok`/`partial` `listing-scan` run in `pipeline_runs` yet) announces itself at INFO with the geography name, the cities and a rough duration (about an hour per 500 homes for sale), and evaluates no alert rules (§4.5, 09 §1); a later scan just lists the cities. Every scan logs `<city> (i/n): <type>` as each fetch starts, so a user watching `make load` sees where it is. For each city in the geography (`settings.target_cities`; location string `"<city>, <ST>"`; sequential, with a 2–5 s jittered sleep after every fetch — three per city), via HomeHarvest, `property_type=['single_family']`:
- `for_sale` (full active inventory)
- `pending` (past_days=45)
- `sold` (past_days=30 — overlapping windows are safe because sales UPSERT on `(property_id, sale_date)`)

Per scraped record:

### 4.1 Resolve → property (see §5)
### 4.2 UPSERT listing
Key `(source='realtor', source_listing_id)`. On first insert: `original_list_price = list_price`, `first_seen = now`, emit `new` event. Always update `last_seen`, `raw`. `raw` is the whole source record minus `primary_photo`/`alt_photos` (already first-class in `photo_urls`), NaN/NaT coerced to null and nested lists/dicts (the advertiser phone lists) kept as JSON rather than stringified, so the column round-trips — it is how source fields we don't model yet (`mls_status` contingency detail, `hoa_fee`, `estimated_value`, `price_per_sqft`, the listing description) and the listing side (`agent_*`, `office_*`, `broker_name`, `mls`/`mls_id` — read by `hb/listing_contact.py`, 07 §Listings) survive ingest. A `raw`-only change is audit metadata: it emits no event and does not count toward `items_upserted`, so the §1 re-run contract still holds.
### 4.3 Status & price transitions
Map source status → ours. `sold` records also UPSERT a `sales` row (`(property_id, sale_date)` key) with `sp_lp = sold_price / original_list_price` (use our stored original if the source's is missing) and `had_price_cut` from event history. The **transition** into `sold` also clears `listings.viewed_at`, so a home read while it was on the market returns to the sold feed unread — the sale price is the new thing to read (08 §2b). This fires on the transition only, never on `status == 'sold'`: the sold window is a rolling 30 days, so a state-triggered clear would wipe the stamp daily for a month and the row could never be marked read. Re-run safe for the same reason as §4.4 — the second run diffs against the already-updated row, sees no status change, and clears nothing.
### 4.4 Diff-only event emission (dedup-critical)
Compare incoming vs stored listing field-by-field; emit `listing_events` ONLY for observed changes: `price_change` (old≠new list_price), `status_change`/`pending`/`sold`, `delisted` (an active listing absent from today's full for_sale scan for that city AND not pending/sold → mark delisted, delist_date=today), `back_on_market` (pending→active). No change ⇒ no event. All events in one run share one `observed_at`, making the event unique key `(listing_id, event_type, observed_at, new_value)` idempotent under re-run (second run diffs against already-updated rows → no diffs → no events).
### 4.5 Scan tail, in order: relist stitching (§6) → `sales.cumulative_dom` sync → auto-enrich of tracked homes (§7) → alert-rule evaluation (09 §2) over this run's events → price-history refresh (§11) → photo download (§4.6) → `open-houses` (§4c)
The stitcher writes CDOM to `listing_groups`; the overbid model's stale routing (06 §5.2) and the comp grid read it off `sales.cumulative_dom`, so the sync copies it across for every sale linked to a stitched listing. Runs **after** stitching, writes only on a value change. Auto-enrich runs before the rules so its RentCast comps feed `new_comp_sold`, and the rules run before the long photo tail so a crash mid-download never skips this run's alerts (each run evaluates only its own `observed_at`). A first scan (`_first_scan`) skips the rules entirely: every home is new to the database, not to the buyer (09 §1). Enrich and the price-history refresh are external calls, fully guarded — a failure is logged and never fails the scan.
### 4.6 Photo download (idempotent, when `SAVE_PHOTOS=true`, default true)
For each listing with photo URLs: download to `data/photos/<property_id>/<listing_id>-<n>.<ext>` (n = position in photo_urls). **Skip any file that already exists** — each image is fetched at most once, ever. Record relative paths in `listings.photo_paths`. The scan captures the **full gallery** per listing — HomeHarvest's `primary_photo` + `alt_photos` (a comma-joined URL list from the search result), primary first, deduped; `enrich` (§7) can add more, same rules. Photos come from the listing site's image CDN (`*.rdcpix.com`), not its pages, so this is the one place the scan is not sequential (03 §5 rule 2): `PHOTO_WORKERS` (4) threads fetch in parallel, each pausing 0.3–0.6 s after every file — what a browser does to show one gallery. A 429/503 from the CDN pauses every worker (`_Throttle`: `PHOTO_BACKOFF_S` = 5 s, doubling to 60 s, reset by the next success) and the file is retried up to `PHOTO_RETRIES` (3) times. A dropped or timed-out connection (`httpx.TransportError`) or another 5xx is one request's bad luck, not a CDN-wide signal: that worker alone pauses `PHOTO_RETRY_PAUSE_S` (2 s, doubling per attempt) and retries, up to the same `PHOTO_RETRIES`. A 403 is the throttle's call (`_Throttle.refused`): the CDN's rate limit answers 403, not 429, to every request, so `PHOTO_BLOCK_AFTER` (8) of them in a row with no success between pauses every worker `PHOTO_BLOCK_PAUSE_S` (60 s, doubling per round), and when it is refused again after `PHOTO_BLOCK_ROUNDS` (3) pauses the tail stops for this run with one WARNING line, the run is `partial` (`photos: the CDN refused requests (403); N left for the next scan` in `error_summary`) and the next scan fetches what is missing; a lone 403 is that file's problem and is skipped. A 4xx other than 403/429 means the file is gone, and that or any other failure is a per-item error (partial-tolerant, retried next run because the file won't exist yet). Workers only fetch and write files; `photo_paths` is updated on the main thread afterwards, in gallery order, from what is on disk. Ctrl+C cancels the queued downloads instead of draining them. This tail is still the slow part of a first run (a city with 500 active listings has ~15,000 photos → about an hour), so it logs how many files are pending before it starts, with a rough duration from `PHOTO_RATE_GUESS` (5 files/s, what four workers and the pause give), a progress line with the measured remaining time every `PHOTO_PROGRESS_EVERY` (200) files, and a closing line with the count and elapsed time; nothing is logged when every file is already on disk. Photos are served only at the local API's `/photos` route and are never redistributed (03 §5.4).

### 4.7 Signals parsed from the public remarks (`hb/pipelines/listing_text.py`)
HomeHarvest returns the listing description as `text` (present on ~100% of peninsula inventory). Two fields exist nowhere else in any free source:

- **`properties.condition_tag`** — the CMA condition adjustment (06 §4.2) and the `f_cond` similarity factor are no-ops while every tag is NULL. Keyword classes are scored by **distinct merged phrase spans** (overlapping patterns like `remodeled` / `remodeled kitchen` count once; a word repeated twice is one claim), a tie across classes returns unknown, and `renovated` needs **2** signals where `fixer`/`dated` need 1. That asymmetry is measured, not arbitrary: peninsula copy is relentlessly promotional, and admitting "beautifully updated"/"updated kitchen"/"designer" as evidence tagged **57%** of live inventory renovated — a +7% adjustment on half the comp pool, worse than no tag. Restricting to verifiable claims (`remodeled`, `renovated`, `new roof/HVAC`, `newly built`, `turnkey`, `permitted addition`) lands at ~13% renovated / ~1.5% fixer / ~1.5% dated / ~84% unknown. **Silence is the design goal** — a wrong tag moves a comp, a missing one merely leaves the adjustment at zero.
- **`listings.offer_due_at`** — parsed only from an explicit trigger ("offers due", "offer date", "submit offers by") followed by a date that anchors to `list_date` and lands in a plausible window. **Measured yield on live inventory: 0%.** Realtor.com's *public* remarks do not carry offer dates — of 154 listings mentioning "offer", every one was the verb ("this home **offers** 1,844 square feet"), which the trigger correctly rejected. The parser stays because it costs one regex and abstains cleanly, but offer dates remain effectively an MLS/agent-comms field (03 §3.3). No deadline is ever guessed (such as `list_date + 7`): a guessed one would fire the posture model's +0.25 log-odds "offer date passed" signal (06 §5.6) on every listing older than nine days.

Provenance without a schema change: inferred tags write `condition_notes` prefixed `auto: ` with the phrases that fired. Any tag whose note lacks that prefix (including a tag with no note) is hand-entered and is never overwritten — a walk-through beats a copywriter. `offer_due_at` is fill-only for the same reason.

**Duplicate-handling acceptance for this job** (restated from §1): second consecutive run ⇒ 0 upserted rows changed, 0 events; the same physical home appearing via both a Realtor.com scan and an `enrich` record (§7: Realtor.com details or a RentCast comp) resolves to ONE `properties` row with two entries in `source_ids`.

## 4c. `open-houses` (run in `listing-scan`'s tail; standalone rerun `hb pipeline open-houses`)

Scheduled open-house slots for the homes the scan stores. `listing-scan` calls it after its own run closes (own `pipeline_runs` row; `JobRunner` swallows its failures, so it never fails the scan). It is not in `DAILY_SEQUENCE` because every slot attaches to a listing the scan stored that morning.

For each source named in `OPEN_HOUSE_SOURCES` (default `realtor,redfin`), in that order, for each city in the geography (one `runner.item` per source × city — a failed fetch is a per-item error):
1. `source.fetch(city, bbox)` → `OpenHouseRecord`s. `bbox` is the lon/lat envelope (+~500 m) of the city's stored active homes, for sources that search by area; `None` when none have coordinates.
2. **Match** each record to an `active` listing: on `(listing_source, source_listing_id)` = `listings.(source, source_listing_id)` when the record carries it (Realtor), else on `(mls_id, zip)` = `listings.raw.mls_id` + `properties.zip` (Redfin — portals share the MLS number, not each other's ids). A record with no stored active listing (not single-family, outside the scan's cities, or not scanned yet) is counted, logged, and skipped — the next run picks it up.
3. **UPSERT** `open_houses` on `(listing_id, start_at)`; `last_seen` always refreshes; `items_upserted` counts inserts and real field changes only, so an unchanged re-run reports 0. A slot an earlier source already wrote this run is **not** rewritten by a later one (only its `last_seen` refreshes), so it stays credited to the first source and keeps that source's description.
4. **Cancellation sweep** — once, after every source, and only when every source × city fetched cleanly: delete **future** slots (`start_at > now`) that no source reported this run. That covers a cancelled slot and every slot of a home that went pending or delisted. A slot on the buyer's schedule (`scheduled_at` set) is not deleted but stamped `cancelled_at`, so the schedule shows the visit is off instead of losing it; the upsert in step 3 writes `cancelled_at = NULL`, so a slot that comes back is revived. Any failed fetch skips the sweep (a transient outage must never wipe the calendar). Past slots are never deleted.

**Realtor source** (`hb/open_houses/sources/realtor.py`): HomeHarvest's search query already selects `open_houses { start_date end_date description time_zone dst href methods }`, but its pandas output drops the column — so the source calls `scrape_property(..., listing_type="for_sale", property_type=["single_family"], return_type="pydantic")` and reads `Property.open_houses`. The listing id uses listing-scan's own precedence (`listing_id → mls_id → property_id`, `_source_listing_id`), so keys cannot drift. Realtor reports **naive local wall-clock** times plus a zone abbreviation that stays `"PST"` year-round (with a separate `dst` flag); `localize()` maps US abbreviations to IANA zones (`PST`/`PDT` → `America/Los_Angeles`, …), which decide DST from the date itself, and falls back to the geography's `timezone` (`geography.toml`, `settings.timezone`) for a missing or unknown zone. Measured on live inventory (Oct 2026): ~10% of active single-family homes carry slots, almost all Sat/Sun 1–4 PM, some weekday twilight slots; 12 cities → ~130 slots per run. Realtor's feed misses many slots the MLS publishes — for San Mateo single-family homes on 2026-10-24, Realtor had 28 homes with an open house and Redfin 71 — hence the Redfin source.

**Redfin source** (`hb/open_houses/sources/redfin.py`): one `GET https://www.redfin.com/stingray/api/gis` per city with `al=1, status=1 (active), uipt=1 (house), num_homes=350, v=8, poly=<bbox ring>` plus the paging/sort/sale-type params Redfin's own map sends (`ord=redfin-recommended-asc, page_number=1, start=0, sf=1,2,3,5,6,7, mpt=99`) — without those Redfin ignores `poly` and answers for whatever region it snaps the box to. It is a polygon search, so no Redfin region ids are needed. Redfin returns 403 to plain HTTP clients, so the request goes through `curl_cffi` with `impersonate="chrome"`; the body is JSON behind a `{}&&` prefix. A response that hits the 350-home cap is split into quadrants (up to 4 levels) and homes seen twice on a quadrant edge are deduped. Each home with `openHouseStart` yields one record: `mlsId.value` + `zip`, start/end from epoch milliseconds (already UTC), `openHouseEventName` as the description, method `in_person`, no event link. Redfin's search exposes only each home's **next** slot, so a later slot only Redfin knows about (a Sunday after a Saturday) appears once the earlier one has passed; Realtor's full slot list still covers the homes it reports. 2–5 s jitter before each request. Test seam: `fetch_gis(params)`.

### 4c.1 Extension points (`hb/open_houses/`)
Three small Protocols, one shipped implementation each, so a deployment in another market swaps a piece without touching the pipeline or the API:

| Protocol | Shipped implementation | Swap by |
|---|---|---|
| `OpenHouseSource` (`sources/base.py`): `name: str`; `fetch(city, bbox) -> Iterable[OpenHouseRecord]` | `RealtorOpenHouses`, `RedfinOpenHouses` | a module under `sources/` + one line in `sources/__init__.py` `REGISTRY`, then list its name in `OPEN_HOUSE_SOURCES` (unknown names fail the run loudly) |
| `Geocoder` (`geocode.py`): `geocode(address) -> GeoPoint \| None` | `CensusGeocoder` — US Census Bureau `onelineaddress`, free, no key, US only | assign `geocode.GEOCODER` |
| `TravelEstimator` (`route.py`): `minutes(a, b)`, `miles(a, b)` | `HaversineEstimator` — straight-line miles × `detour_factor` (1.3) at `avg_mph` (25); the API builds it from `ROUTE_DETOUR_FACTOR` / `ROUTE_AVG_MPH` in `.env` (`config.py`), which default to the same numbers | pass `estimator=` to `plan_route` / `drive_legs` / `suggested_order` (e.g. a routing-API client) |

**Adding an open-house source** — implement `fetch` to yield `OpenHouseRecord(start_at, end_at, listing_source, source_listing_id, mls_id, zip, description, href, methods)` with **timezone-aware** times (use `localize()` for naive wall-clock input). Give either `listing_source` + `source_listing_id` equal to how some listing pipeline stores that home in `listings.(source, source_listing_id)`, or the home's `mls_id` + `zip` — those are the only joins. Raise from `fetch` to fail the city. Tests monkeypatch the source's own `fetch_*` seam; `conftest.py` stubs the Realtor and Redfin seams for every test, because `listing-scan`'s tail runs this job.

**Day routes** (`route.py`): the buyer sets each day's visiting order (`open_houses.schedule_position`), and `drive_legs` times the drive into each stop in that order — every stop is kept and no visit times are computed; a home with no coordinates gets no leg and the next leg starts from the last located stop. **Auto-order** is `suggested_order`, built on the planner `plan_route`: stops carry their time windows; the planner tries every visiting order up to 8 stops (40,320 orders — instant) and falls back to greedy "soonest finish from here" above that. Each order is walked from home, waiting for a window to open and passing over a stop that can't get the full dwell (default 20 min) before it closes (`open only N min`, `can't get N min before it closes`, `closed before you'd arrive`). The best order visits the most stops, then drives the least, then gets home earliest. `suggested_order` returns that order followed by every stop it couldn't fit (and any without a location), soonest window first — a suggestion the buyer can rearrange, never a filter. The Google Maps link holds origin + 9 waypoints + destination, so it covers a day's first 10 stops.

## 5. Entity resolution (`resolve.py`)

Normalization: `usaddress-scourgify`'s `normalize_address_record()` → uppercase line1, unit split out, ZIP5. Store raw input in `properties.source_ids.raw_addresses`.

Match cascade (first hit wins):
1. **Exact**: `(address_norm, zip, unit)` equality.
2. **Fuzzy** (guarded): same ZIP AND same house number (the leading token of normalized line 1 — neighbours on a tract street share a floor plan, so distance, sqft and a one-digit string difference all pass for two different homes) AND haversine(lat,lon) < 100 m AND (|Δsqft| ≤ 5% OR either sqft NULL) AND RapidFuzz `token_sort_ratio(street strings) > 92`. Skip fuzzy entirely if incoming lat/lon is NULL.
3. **Create** new property.

On match: fill NULL property fields from incoming data and append the source id. A different non-NULL value is logged as a conflict in `source_ids` (`{field, kept, seen}`) and never overwritten — with one exception: a record from a listing on the market (`listing-scan` passes `authoritative=True` for its for-sale and pending records) is the freshest description of the house, so its `beds`/`baths`/`sqft`/`lot_sqft`/`year_built`/`property_type` replace the stored values, logged as `{field, kept, replaced}`, and any earlier conflict entry that recorded the replaced value is dropped. A renovation or addition changes exactly these fields, and without the rule a flipped home would show its pre-remodel size at its post-remodel price. Address fields are never revised, and sold, backfill and enrichment records only fill gaps. This cascade is pure-functional over inputs + DB state and unit-tested with a fixture matrix (10 §2).

## 6. Relist stitching (`relist.py`)

Goal: true cumulative DOM per property across delist/relist games.
- Trigger: after each scan, for every property touched today.
- Rule: order the property's listings (any source) by list_date. A new episode starting < 90 days after the previous episode's delist_date (and no intervening sale) joins that episode's `listing_group`; emit `relisted` event on the new listing. Gap ≥ 90 days or intervening sale ⇒ new group (UI still shows "previously listed N days, delisted <date>").
- `cumulative_dom` = Σ over member episodes of `min(end, today) − list_date` in days, where end = delist/pending/sold date.
- Deterministic recompute: the stitcher rebuilds group membership + cumulative_dom from the listings table each run (no incremental state to corrupt) — re-running changes nothing.

## 7. `enrich` (on-demand + auto for tracked)

`hb pipeline enrich --property-id X` (UI button) and automatically for all `tracked_listings` (stages saved→offered) once per day within the scan run:
1. **Realtor.com** (free, no key): a `GetHomeDetails` query to the frontdoor GraphQL (`realtor_gql.py`; the scan-stored mpr id when there is one, else an address resolve) → home-value estimate → `avm_snapshots (source='realtor_estimate', as_of=today)`, details (fill property NULLs via §5 merge rules) and gallery photo URLs (downloaded per §4.6) — the `(property_id, source, as_of)` key makes daily re-runs idempotent. Redfin's stingray API sits behind a WAF and 403s every request, so it is not a source.
2. **RentCast** (needs `RENTCAST_API_KEY`; budget-guarded, 03 §3.1): `/avm/value` → snapshot `source='rentcast'` + the returned comps persisted as `sales` rows (`source='rentcast'`) keyed `(property_id, sale_date)`.
3. Optional Zestimate via a RapidAPI Zillow wrapper when both `ZILLOW_WRAPPER_ENABLED` and `RAPIDAPI_KEY` are set → snapshot `source='zestimate'`.
Rate limit: ≥ 1 s jittered sleep between external calls.

## 9. `schools` (daily cadence, hash-noop like the other bulk jobs)

Pull every public school in the geography's state (`LSTATE = settings.geo.state`; name, level, lat/lon, district, **`leaid`**, **`is_charter`**) from the **NCES Common Core of Data** "School Characteristics" ArcGIS layer (`services1.arcgis.com/.../School_Characteristics_Current/FeatureServer/1`, paged by `resultOffset`), keeping Active elementary/middle/high, and bulk-upsert into `schools` keyed on `nces_id`. `leaid` (the 7-char NCES LEA id) is the exact join key to `school_districts.geoid` — LEA name strings are not safe to join on. Listing detail assigns one school per level via `hb/schools_match.py` (see §12) and returns them as `property.schools[]` — real, free, no-key, covers every listing with no per-listing fetch. NCES ArcGIS is a programmatic API (not bot-walled like the CDE web export). A content hash of the fetched rows drives status=noop when unchanged. `rating` is filled by §10 (on-conflict upserts here never clobber a set rating).

## 10. `school-ratings` (standalone; annual CAASPP data, run manually — NOT in the daily sequence)

`hb pipeline school-ratings`. Download the **CAASPP Smarter Balanced** research files from ETS (`caaspp-elpac.ets.org/caaspp/researchfiles/`): the all-CA results file (~157 MB zip) and the small entities file. DuckDB-aggregate the results to each school's average **% Standard Met and Above** across ELA + Math (Student Group 1 = all students, Grade 13 = all grades), map to a **1-10 decile** (percentile rank across CA schools), and join onto `schools` by `(zip, normalized name)` — the entities file supplies the zip per CDS. Sets `schools.rating` (fast-path column) **and** upserts a `source='caaspp'` row into `school_rating_snapshots` so the API serves all rating sources uniformly; unmatched schools (~9%) stay NULL. Standalone because CAASPP updates yearly and the file is large; bump `CAASPP_YEAR` in `.env` after each release. **Pack-gated**: the job runs only when the current pack's `rating_sources` declare `caaspp` (`hb/packs/ca/sources.py`); under any other pack it records a `noop` without downloading anything, and ratings come from the other sources. The ~1 GB extracted results CSV is deleted after aggregation (the zips stay in the raw cache). Content hash of the two file digests drives status=noop.

## 11. `price-history` (populated by the scrapes; standalone backfill available)

Fetches each property's **Realtor.com sale/listing history** and caches it on `properties.price_history` (a JSON list of `{date, event, price}`, newest-first) + `price_history_fetched_at`. The listing-detail API returns this column directly — **no external call on page load**. Source: a minimal `GetHomeDetails` GraphQL query to `realtor.com/frontdoor/graphql` (browser headers, no auth — the same endpoint the scan uses) for the `property_history` node homeharvest omits, keyed on the Realtor mpr_id the scan already stored in `source_ids["realtor"]` (address-search fallback otherwise). Scraping → degrades to `[]` on any failure.
- **During the scan** (`listing_scan.run`): `price_history.refresh_many(session, touched_properties ∪ watched)` runs in the external tail (guarded, next to enrich + photo download), refreshing every scraped property — and every Watchlist home (`hb.watchlist.watched_property_ids`, 08 §5b), scraped or not — whose cache is missing or >7 days stale, then replays the result onto sales via §14. The Watchlist half matters because a delisted home drops out of the city scan: its Realtor history is then the only place a later off-market sale appears, and the Watchlist reads a `Sold` entry dated on/after the current episode's `list_date` as that home's outcome (`sold_source='public_record'`, 07 §Watchlist). The 7-day gate makes this a weekly fetch per watched home.
- **Standalone** `hb pipeline price-history [--limit N]` backfills **current inventory *and* the comp pool** (any property with an on-market listing OR a sale), then runs the §14 derivation in its own tail so the fetch and the thing it exists to feed never drift apart. The comp half is the point: §14 repairs `sales`, and comps are by definition sold, so an inventory-only scope would leave the overbid model exactly as blind. Never-fetched properties sort first, so `--limit` gives resumable chunks that always advance. Rate-limited ~1 s between calls — a full pass over the current DB is several hours.

Concurrency note: the SQLite engine now sets `PRAGMA busy_timeout=5000` (`db/engine.py`) so this scrape (and any pipeline) can write while the API server is running instead of failing with "database is locked".

## 12. `school-districts` (daily cadence, hash-noop; boundary-aware school matching)

Pull every school-district boundary polygon in the geography's state (`STATEFP = settings.geo.state_fips`) from the **NCES TIGER** "School Districts - Current" ArcGIS layer (`services1.arcgis.com/.../School_Districts_Current/FeatureServer/0`, `f=geojson`, paged) and bulk-upsert into `school_districts` keyed on `geoid` (= LEAID). `kind` (elementary | secondary | unified) is derived from `ELSDLEA/SCSDLEA/UNSDLEA`; non-operational (`FUNCSTAT != 'E'`) and pseudo-districts (`SDTYP` set) are skipped. Geometry is stored as GeoJSON text with bbox columns; ~940 polygons for California, TIGER vintage bumps ~annually so daily runs hash-noop.

**Matching** (`hb/schools_match.py`, called by listing detail): a process-cached shapely `STRtree` over the polygons (rebuilt only when the table changes — cache key is `(count, max(updated_at))`); point-in-polygon finds the property's governing districts (a unified one, or an overlapping elementary + secondary pair — split-district geographies like the Peninsula's are exactly why nearest-distance picked wrong schools). Per level: elementary/middle → elementary-else-unified district, high → secondary-else-unified; the pick is the **nearest non-charter school with that `leaid`**. Fallback ladder, flagged per row via `assignment`: `district` (polygon match) → `nearest` (no polygon or no in-district school of that level; the pre-boundary 15-mile behavior) → `zip` (no coordinates; top-rated in ZIP). True school-level *attendance zones* have no current free source (NCES SABS ended 2015-16), so nearest-within-district is the school-level heuristic. Matching is read-time + cache rather than a precomputed table, so it never goes stale for newly scanned properties.

## 13. `schooldigger-ratings` (daily cadence — converges across runs under the API day-cap, noop when fresh)

`hb pipeline schooldigger-ratings`. Second rating source next to CAASPP (the only one outside California): **SchoolDigger** statewide rankings for the geography's state (`st = settings.geo.state`, logged at job start — a wrong state burns the day's quota) via their sanctioned v2.4 API (`appID`/`appKey` — free developer plan at developer.schooldigger.com; set `SCHOOLDIGGER_APP_ID`/`SCHOOLDIGGER_APP_KEY`). The free plan is hard-capped at **20 calls/day** (`x-dayrate-limit` headers) and `/v2.4/schools` has **no county filter** (unknown params silently ignored), so the job converges across daily runs: it queries per **district** (`districtID` = our `school_districts.geoid`, 1-3 calls each), targeting only districts actually assigned to properties in the DB (point-in-polygon via `hb.schools_match`, ~20 districts), and keeps per-district completion dates in `settings` key `schooldigger_progress` (re-fetched after 180 days — rankings are annual). Day-scoped budget guard (`settings` key `schooldigger_budget`, `SCHOOLDIGGER_DAILY_LIMIT`, default 18); hitting the guard or an API 429 stops cleanly (done districts keep their snapshots; rerun tomorrow — noop if nothing was fetched); missing credentials ⇒ clean noop. Matching is by NCES id (SchoolDigger school ids are NCES ids) with `(zip, normalized name)` fallback. Rating semantics (verified live): `rankHistory[0].rankStatewidePercentage` = "ranks above X% of the state's schools" (high = good, consistent with `rankStars`), normalized `round(pct/10)` clamped 1-10 onto the badge scale; native label "#123 of 5,856 in CA" preserved. Why not GreatSchools/Niche: GreatSchools' 1-10 rating requires a paid enterprise license (the ratings on Zillow/Redfin are that same licensed data), Niche has no API, and scraping any of them violates ToS.

## 14. `derive-sales-history` (pure derivation, no network; run in `price-history`'s tail)

`hb pipeline derive-sales-history` (`hb/pipelines/sale_history.py`). Replays each property's cached `price_history` timeline onto its `sales` rows to recover the listing history the scan is structurally unable to have observed. Motivation: the daily scan only sees what happens after it starts running, so every comp from `backfill-sales` or a closed-record scrape carries `had_price_cut=False`, a *final*-list-price proxy for `original_list_price`, and a NULL `cumulative_dom` — and 06 §5.2 splits comps into fresh vs stale on exactly those fields, with the fresh distribution carrying 0.8 of the blended prediction weight. Left uncorrected the whole comp pool reads as "fresh".

**Campaign semantics mirror §6.** Events are windowed to `(previous sale, this sale)` so an earlier ownership cycle can never leak in, split into episodes at each `Listed`/`Relisted` event, then clustered by the same `RELIST_GAP_DAYS` (90) rule the stitcher uses — consecutive episodes closer than that are ONE marketing campaign. So `original_list_price` is the first list price of the *campaign*, not of the final episode: a seller who delists and relists lower has still cut, and 01 §3 requires SP/LP against the original. Rental episodes are ignored outright; an episode's exposure ends at its first `Sold`/`Pending`/`Removed`/`Off Market` event (a price change does **not** end it), matching `relist._episode_end`. `dom` = the final episode's span; `cumulative_dom` = the sum across the campaign.

**Write policy** — reconstruction never overrides observation (04 §sales): `had_price_cut` only False→True, `original_list_price` only ever raised (with `sp_lp` recomputed), `dom`/`cumulative_dom` fill NULLs only. That makes the job idempotent: a second consecutive run changes zero rows.

Coverage is bounded by how many properties have a cached timeline, which is why §11's backfill scope includes the comp pool.

## 15. `deal-deadlines` (daily cadence, pure DB read — closing deadline alerts)

`hb pipeline deal-deadlines` (`hb/pipelines/deal_deadlines.py`). Walks every `deals` row with `status='open'`, recomputes its schedule with `hb/closing_spec.py` (`evaluate()`), and emits `deal_deadline_soon` / `deal_deadline_overdue` rows (09 §2).

**Why it is its own job rather than part of `listing-scan`'s rule pass.** Every other alert is event-driven — something changed upstream and the rules noticed. These are *calendar*-driven: the contingency date arrives whether or not anything was scraped that morning, and the failure mode being guarded against (a missed contingency removal, 14 §4) costs the earnest-money deposit. It must fire on a quiet day, and it must not depend on the user opening `/closing`.

**Daily-safe by construction**: no network, no writes outside `alerts`, and each `dedup_key` carries the task key, the resolved due date and the alert bucket — so re-running the same day inserts nothing. Because the due date is *in* the key, correcting `accepted_on` re-dates the task and legitimately re-alerts against the new date. `noop` when no deal is open or both rules are disabled.

**Scope rules** (mirroring the spec's own pruning, so nothing alerts about a task that does not exist for this deal): completed and waived tasks are skipped; tasks belonging to a waived contingency are already absent from the schedule; and only `blocking` tasks raise the *overdue* alert.

## 16. `hazards` (daily cadence, hash-noop) and `hazards-fetch` (standalone, once)

`hb pipeline hazards-fetch` (`hb/pipelines/hazards_fetch.py`) downloads the hazard polygon layers the current pack declares (`packs.current().hazards`, `HazardLayer` records — 03 §1.4, `docs/packs/README.md`) as GeoJSON to `data/raw/hazards/{key}.geojson` (not date-dirred; reference data). Each layer's `query(geo)` scopes the ArcGIS REST query to the geography: FEMA NFHL by `DFIRM_ID IN ('<state fips><county fips>C', …)` from `geo.dfirm_ids`; the `ca` pack's CAL FIRE / CGS layers by the `[market].hazard_bbox` envelope. Pages of 2000 with ~1 s jittered sleeps; a layer whose features are byte-identical to the file on disk is left untouched, and the run is `noop` when nothing changed. `--if-missing` (`run(missing_only=True)`, what `make load` passes) skips a layer whose file exists without fetching it at all, so the first `make start` downloads every layer and later ones cost nothing. Not in `DAILY_SEQUENCE` — rerun without the flag when a state re-releases zones. `fetch_layer(url, params)` is the test seam.

`hb pipeline hazards` (`hb/pipelines/hazards.py`, in `DAILY_SEQUENCE`) loads those files into one STRtree per layer and point-in-polygon tests every property with coordinates, upserting presence-based `hazard_flags` rows keyed `(property_id, hazard)` with `zone_value = layer.zone_value(feature.properties)` (FEMA: `FLD_ZONE` plus the subtype; CAL FIRE: `FHSZ_6Class`; CGS: the quad name, since those layers carry no severity). Content hash = digest over the files' sha256s: unchanged files ⇒ only properties with no flags yet are checked (new since the last run), none ⇒ `noop`; changed files ⇒ full reprocess. `checked_at` is excluded from the upsert values so an unchanged re-run touches zero rows (D1). Missing files fail the run with a pointer to `hazards-fetch`. The listing page, Compare and the brief label each flag through the pack's layer registry (`GET /api/config` → `pack.hazards`), so a state pack that adds a layer needs no UI change.

## 17. `backfill-sales` (standalone, run once after install)

`hb pipeline backfill-sales [--months 24] [--date-from YYYY-MM-DD] [--date-to YYYY-MM-DD]` (`hb/pipelines/backfill_sales.py`; `make backfill MONTHS=36` wraps it). The daily scan only pulls `sold` records from the last 30 days, so a fresh install has no deep sales history — and the golden backtest (10 §4) needs comps that closed *before* each list date. This job pulls closed single-family sales via HomeHarvest over a wide window — `--months` back from today by default (24), or an explicit `--date-from` / `--date-to` (`--date-from` overrides `--months`; `--date-to` defaults to today) — per city, with the scan's 2–5 s jittered sleep between cities, and upserts them straight into `sales` (`fetch_sold(city, date_from, date_to)` is the test seam).

Comp-only by design: it resolves properties and writes `sales` rows but creates **no** `listings`, `listing_events` or alerts — years-old solds must not spam the timeline or the inbox. A gap-filler, never an updater: a row that already exists on the `(property_id, sale_date)` key is skipped untouched, because the scan's event-derived truth (`had_price_cut`, pre-cut `original_list_price`, `sp_lp` against the original) is strictly richer than what a historical sold record exposes. Run `build-index` afterwards (`make build-index`) so the price index sees the new history; §14 later repairs the backfilled rows' price-cut history and CDOM from the Realtor timelines.

## 18. `hb db backup` (the nightly backup, by hand)

`hb db backup` (`hb/db/backup.py`) is the same step `hb pipeline daily` takes in its tail (§2): sqlite3's online backup API (safe under WAL, no downtime) writes `data/backups/hb-<YYYY-MM-DD>.sqlite3` — a same-day re-run overwrites — and prunes files older than 14 days. Restore and the rest of the ops story are in 11 §2.
