# 07 — API Spec

FastAPI, all routes under `/api`, plus one static mount: **`/photos/{property_id}/{filename}`** serving `data/photos/` (local images downloaded per `05-pipelines.md` §4.6; never exposed on an unprotected deployment). `hb serve` also serves the built SPA from `frontend/dist` (`main.py`): `/assets` as a static mount, and a catch-all route that returns a file from `dist` when one matches, a 404 for any other path with a file extension, and `index.html` for extension-less deep links (a plain "not built yet" page when `frontend/dist` is missing). JSON only. No auth (single user; network-level protection when deployed). Errors: FastAPI-standard `{"detail": ...}` with 404/422. Money = integer dollars; dates ISO-8601. Pagination: `?limit=` (default 100) `&offset=` where noted.

## Market (`api/market.py`)
- `GET /api/market/summary` → target band + per-target-ZIP latest metrics for Dashboard tiles:
  `{target_band: {min, max}, zips: [{geo_id, city, metrics: {median_sale_price, median_ppsf, avg_sp_lp, median_dom, inventory, months_supply, months_supply_live}, deltas_90d: {…same keys, pct change vs ~90 days earlier}, sources: {…same keys → 'redfin'|'derived'|'derived_city'|null}}]}` (avg_sp_lp is Redfin's published average sale-to-list. `months_supply_live` is the default 3-month window (`period='3m'`, 05 §3.5). `sources` carries the provenance of each latest value — `derived_city` means the ZIP was too thin and the parent city's figure is shown, which the UI must badge.)
- `GET /api/market/supply?window=3` → months of supply per target geo, for the Supply page (08 §9). `window` is the live series' trailing window in months: `3|6|9|12`, default 3, anything else 422.
  `{as_of: {redfin_window_start, redfin_window_end, live, live_window_months}, zips: [SupplyGeo], cities: [SupplyGeo]}` where `SupplyGeo = {geo_id, city, months_supply, months_supply_basis, months_supply_live, months_supply_live_basis, delta_90d, pct_rank_3y, band: 'very_tight'|'tight'|'balancing'|'soft'|'unknown'}`. `months_supply` is Redfin's published rolling 3-month figure (`months_supply_basis='redfin'`); `band`, `delta_90d` and `pct_rank_3y` describe that series (the one with years of history, 06 §9). `months_supply_live` is the now-cast for the requested window (`period=f'{window}m'`), `months_supply_live_basis` is `'derived'` or `'derived_city'` (borrowed from the parent city because the ZIP had too few closed sales in the window), and it stands alone — a window with no rows for a morning returns null rather than another window's value. `cities` carries the same two figures rolled up to the city — the values a thin ZIP borrows.
- `GET /api/market/series?geo_type=zip&geo_id=94087&metric=median_ppsf&period=3m&since=2023-01-01` → `[{period_start, value, source}]`. `period` is an optional filter (the route never requires it): omit it for Redfin metrics (one series per geo) and pass it for `months_supply_live`, which is stored once per window (`3m|6m|9m|12m`, 04) — without it every window's rows come back interleaved.
- `GET /api/market/rates?series=MORTGAGE30US&since=...` → `[{date, value}]`

## Listings (`api/listings.py`)
- `GET /api/listings?status=active,pending&city=Sunnyvale&zip=94087&q=&min_price=&max_price=&min_sold_price=&max_sold_price=&min_beds=&has_price_cut=&min_cut_pct=&stale_only=&sort=list_date|price|sold_date|sold_price|cdom|cut&limit=&offset=` →
  (`status` accepts a comma-separated list of `active|pending|sold|delisted`, or `any`; default `active`; `city` is comma-separated; `min_sold_price`/`max_sold_price` bound `sold_price` for the sold feed; `limit` default 100, capped at 500; every sort is descending)
  `q` is free text: every whitespace-separated token must match `address_norm`, `city` or `unit` (case-insensitive substring) **or** the ZIP as a *prefix* — a substring ZIP match would make any street number in the query collide with the digits inside every ZIP. Tokens are ANDed, so `sunnyvale maple` narrows.
  `has_price_cut` = any reduction (an observed `price_change` **or** a current ask below `original_list_price`); `min_cut_pct` = minimum reduction off the original ask, in percent (`min_cut_pct=5` ⇒ ≥5% off). `sort=cut` orders by `cut_pct` descending.
  `{total, items: [ListingSummary]}` where `ListingSummary = {id, property_id, address, city, zip, lat, lon, status, list_price, original_list_price, sold_price, sold_date (both null until the listing closes), beds, baths, sqft, list_date, dom_source, cumulative_dom, price_cut_count, cut_pct (% below the original ask, derived from `original_list_price` vs the current price so a campaign we started observing mid-flight — or a backfilled row with no event history — still reports its reduction; null when the price never came down), is_relist, predicted_sale: {low, point, high, basis: 'fresh'|'stale', unadjusted_point, rejection_weight} | null, posture: 'underpriced'|'near_market'|'overpriced'|'unknown' | null, posture_confidence: 'low'|'medium'|'high' | null, posture_p_below_list: float | null (P(sells below the current asking price | it sells) — docs/06 §5.6; null without exposure data), photo_url (local `/photos/...` path when downloaded, else source URL), url, tracked: bool, viewed_at (detail-page open in the listing's current status, null = unread), next_open_house: {start_at, end_at} | null (the soonest `open_houses` slot not yet over, UTC ISO; always null unless the listing is active — 05 §4c)}`
- `GET /api/listings/{id}` (side effect: stamps `viewed_at` when it is NULL — opening the detail page is the "viewed" action for the Recently Sold indicators, 08 §2b; `listing-scan` clears it again when the home closes, so a sold listing restamps on its next open) → full detail: ListingSummary + `{photos: ["/photos/..."] (the full downloaded gallery — primary + alt_photos, indexed -0..-N), events: [{event_type, old_value, new_value, observed_at}], listing_group: {cumulative_dom, episode_count, ended_by: 'sale'|'withdrawn'|'open', episodes: [{listing_id, source, list_date, original_list_price (the price the episode opened at, not the live one — a Listed row built from the live price rewrites itself on every cut), pending_date, delist_date, sold_date, sold_price, status}] (oldest-first)} | null, property: {condition_tag, condition_notes, lot_sqft, year_built, assessor_sqft, sqft_mismatch: bool (05 §8), schools: [{name, level: 'elementary'|'middle'|'high', rating: 1-10|null (CAASPP test-score decile; null until the `school-ratings` pipeline runs or a school is unmatched), distance_mi, district (governing district polygon name when boundary-matched, else the school's LEA name), assignment: 'district'|'nearest'|'zip' (boundary point-in-polygon match / nearest fallback / ZIP fallback — docs/05 §12), ratings: [{source: 'caaspp'|'schooldigger'|..., rating_10: 1-10|null, label}] (per-source snapshots, caaspp first)}] (one school per level assigned via `hb/schools_match.py`, elementary→middle→high; [] until the `schools` pipeline runs or if the property has no coordinates and no ZIP match)}, avm_snapshots: latest per source, price_history: [{date, event, price|null}] (newest-first Realtor.com sale/listing history, cached on the property by the `price-history` pipeline/scan; [] until populated), offer_due_at, `tracked_id` + `tracked_stage` (both null when the home is not on the tracker — the detail page's tracker control binds to them, 08 §3), `watching` (bool — the home is on the Watchlist; the detail page's Watch control, 08 §3 1b), hazard_flags: [{hazard, zone_value, checked_at}] (05 §16), posture_detail: {posture, confidence, logit, p_below_list, typical_sold_to_list, exposure: {days, episode_days, episode_count, cuts, cut_source: 'observed'|'history'|'relist_lower'|null, median_dom, ratio, offer_passed}, value_gap_pct (list / unadjusted blend − 1; informational), withdrawal_share, rejection_weight, adjusted: {low, point, high}|null, unadjusted_point, agreement: 'agree'|'moderate'|'diverge'|'unknown', spread_pct, signals: [{id: 'exposure'|'price_cuts'|'relist'|'offer_passed', label, points (log-odds of selling below asking), detail}]} | null (docs/06 §5.6), listing_contact: {agent: {name, email, phones: [{number (ten digits), type: 'mobile'|'office'|'home'|'toll_free'|'other', primary, sms (true for mobile lines)}], mls_id, nrds_id} | null, office: {name, email, phones} | null, broker: {name} | null, builder: {name} | null, mls: {system, id} | null} | null (the listing side off the MLS record in `listings.raw`, normalized by `hb/listing_contact.py` — fax lines dropped, duplicates collapsed, primary first; null when the source carried no advertiser — 08 §3 1c), contacts: [Contact] (rows saved on this listing, `listing_id` set), remarks: string | null (the listing agent's public remarks, verbatim from `listings.raw.text` where the scan keeps them — 05 §4.2; whitespace-trimmed, null when blank or absent), open_houses: [{id, source, start_at, end_at (UTC ISO), description, href, methods: ['in_person'|'virtual'], scheduled, cancelled}] (every `open_houses` slot for this listing not yet over, soonest first — the same slot shape as `/api/open-houses` minus `listing`/`distance_mi`; unlike the list endpoint it **keeps cancelled slots**, which only exist when the buyer had scheduled them, so the page can say the visit is off; `[]` unless the listing is active — 08 §3 1d), timezone (the IANA zone to render those times in: the geography's `timezone`, `settings.timezone`)}`
- `PATCH /api/listings/{id}` body `{offer_due_at?}` (`""` clears) → `{id, offer_due_at}`; 404 on an unknown listing
- `GET|POST /api/listings/{id}/contacts`, `PATCH|DELETE /api/listings/{id}/contacts/{contact_id}` (`api/contacts.py`) — the people behind a listing, stored in `contacts` with `listing_id` set: the listing agent reached before any offer, the owner of record found on the assessor roll. POST body `{kind, name, company?, role?, phone?, email?, notes?}`; PATCH the same, all optional, `""` clears. 404 on an unknown listing or a contact not on that listing; 422 on a bad kind. `Contact = {id, kind, name, company, role, phone, email, notes, deal_id, listing_id}`; `kind ∈ escrow|title|lender|inspector|insurance|attorney|tc|listing_agent|owner|contractor|other` — the one vocabulary shared with the deal team (`hb/api/contacts.py`).
- `PATCH /api/properties/{id}` body `{condition_tag?, condition_notes?}` (`""` clears either) → `{id, condition_tag, condition_notes}`; 422 unless `condition_tag ∈ renovated|dated|fixer|""`, 404 on an unknown property
- `POST /api/properties/{id}/enrich` → triggers enrich pipeline inline; returns `{avm_snapshots, rentcast_quota_remaining}` (null when no `RENTCAST_API_KEY` is set); 404 for an unknown property
- `GET /api/listings/{id}/brief` → `text/markdown` — the AI deep-dive brief (`hb/brief.py`, docs/13 §9): subject (with the listing side's contact and any saved contacts, stated as representing the seller), market position + posture signals, CMA + comps (line items overridden in the workbench carry a trailing `*`; the stored `_overrides` key is never printed), schools/hazards, PITI + offer solver output, the tour record, priced deferred maintenance, **what could not be verified** (every blank checklist item and unasked agent question), what to attach, and a ready-to-paste request. Pure assembly — no new computation.

## Open houses (`api/open_houses.py`, 05 §4c)
- `GET /api/open-houses?from=&to=&max_miles=&city=&min_price=&max_price=&sort=time|distance|price` → `{origin: Origin | null, from, to, timezone, items: [OpenHouse]}`. Non-cancelled slots of **active** listings overlapping `[from, to)` (ISO-8601; a value with no offset is read in the geography's `timezone`). Default window: now → the end of the coming Sunday in that zone (today, if it is Sunday). `max_miles` drops slots farther than that from the origin, and slots with no distance. `city` is comma-separated. `min_price` / `max_price` bound the listing's current `list_price` (inclusive; a home with no list price is dropped by either). `sort=time` is start then distance, `distance` is nearest first (unknown last), `price` is ascending list price. `timezone` is the IANA zone the client must render every time in. `OpenHouse = {id, listing_id, source, start_at, end_at (UTC ISO), description, href, methods: ['in_person'|'virtual'], scheduled (on the buyer's schedule), cancelled (a scheduled slot the source dropped — only ever true in the schedule), distance_mi (straight-line from the origin, 1 dp; null without an origin or coordinates), listing: ListingSummary}` — the same serializer as `/api/listings`, without `predicted_sale`/`posture` (the page shows neither).
- `GET /api/open-houses/schedule` → `{origin, timezone, items: [OpenHouse]}`: every slot with `scheduled_at` set that hasn't ended, in the buyer's order (`schedule_position`, then start time). Unlike the list it keeps cancelled slots and slots whose home is no longer active, so the page can say why a visit is off.
- `PUT /api/open-houses/{id}/schedule` → `{id, scheduled: true}` (idempotent; a newly scheduled slot goes last in the order); `DELETE /api/open-houses/{id}/schedule` → `{id, scheduled: false}`, which deletes the row outright when it is a cancelled slot (only the schedule was keeping it). 404 on an unknown id.
- `PUT /api/open-houses/schedule/order` body `{open_house_ids: [id]}` (normally one day's live stops, in the new order) → `{open_house_ids}`. The slots swap among the positions they already hold, so the rest of the schedule keeps its order. 422 on an empty list or a repeated id; 404 when an id is not on the schedule.
- `GET /api/open-houses/origin` → `{origin: Origin | null}` where `Origin = {address, lat, lon}`. Read from the `settings` row `home_location`. When that row is empty and `HOME_ADDRESS` is set, it is geocoded once and saved (a seed that fails to geocode stays unset, no error).
- `PUT /api/open-houses/origin` body `{address}` → `{origin}`. Geocodes via `hb.open_houses.geocode.GEOCODER` (US Census by default) and saves. 422 on a blank or unresolvable address, 502 when the geocoder is down. `address` is stored as typed, not as the geocoder rewrites it.
- `POST /api/open-houses/route` body `{open_house_ids: [id] (visiting order; a repeated id counts once), optimize? (default false), start_at? (ISO; optimize only — default: whenever the first window opens), dwell_min? (optimize only; default 20)}` → `{origin, total_drive_min, maps_url (Google Maps multi-stop directions from the origin) | null, maps_stops (how many stops the link covers, at most 10), stops: [{open_house_id, listing_id, address, start_at, end_at, drive_min, drive_miles}]}`. `stops` is **every** requested stop, in the order given — or, with `optimize`, in the planner's suggested order (05 §4c.1) — each with the drive in from the previous located stop (from home for the first); there are no visit times and nothing is dropped. A home with no coordinates keeps its place with `drive_min`/`drive_miles` null. 422 on an empty list or when no origin is set; 404 on an unknown id.

## CMA (`api/cma.py`)
- `POST /api/cma/run` body `{property_id (required), params?: {radius_mi?, months?, max_comps?}}` → `CmaRun`; 404 on an unknown property:
  `{id, property_id, subject: {property_id, address, lat, lon, sqft, beds, baths}, estimate, low, high, confidence, confidence_reasons: [...], index_source, as_of, comps: [{sale_id, address, sale_date, sale_price, distance_mi, lat, lon, beds, baths, sqft, condition_tag, similarity_score, auto_selected, included, time_adj_factor, adjustments: {time, sqft, baths, lot, condition}, adjusted_price}]}` (the selected comps plus up to 6 next-best candidates with `included: false` for the workbench drawer)
- `PATCH /api/cma/runs/{id}/comps` body `{sale_id, included}` → recomputed `CmaRun` (new run row persisted, referencing same comp set); 404 when the run or the sale is unknown
- `PATCH /api/cma/runs/{id}/adjustments` body `{sale_id, overrides: {sqft?: int, ...}}` → recomputed `CmaRun` (overrides merge onto the ones already stored for that comp)
- `GET /api/cma/runs/{id}` → the stored run rebuilt as a `CmaRun` (comps included-first, then by score; `as_of` is the run's creation date; `confidence_reasons` from the persisted params); 404 on an unknown run
- `GET /api/cma/runs?property_id=` (required) → `[{id, created_at, estimate, low, high, confidence, index_source, n_comps}]`, newest first

## Overbid (`api/overbid.py`)
- `GET /api/overbid/{listing_id}` → `{list_price, basis: 'fresh'|'stale', basis_reason, n_comps, n_eff, window_days, p25, p50, p75, predicted: {low, point, high}, atypical_pricing: bool, histogram: [{bucket_low, bucket_high, weight}], comps: [{address, sale_date, sp_lp, original_list_price, sale_price}]}`. `p25/p50/p75` are the raw weighted quantiles; `predicted` is the **calibrated range** (widened per `06-algorithms.md` §5.4) with point = list × p50, where `list_price` is the anchor the model scales from — the listing's `original_list_price`, falling back to the current `list_price`.
- **`predicted_sale` on ListingSummary** (listings/tracker/detail) is served by `valuation.predicted_sale`: the calibrated range with its **point blended** (`valuation.CMA_WEIGHT`·latest-CMA + rest·overbid point), then **market-evidence-adjusted** (docs/06 §5.6 — pulled toward list when prolonged exposure says the price was rejected). `unadjusted_point` carries the pre-adjustment blend and `rejection_weight` (0..1) says how hard it was pulled; the same adjusted number is what the golden backtest gates mid-flight. Range widened to contain the point when a divergent CMA pulls it outside. **Page cache**: `attach_predicted` builds one `cache` dict per request and threads it through `valuation.predicted_sale` → `overbid.predict` / `posture.classify` → `exposure.inputs`, memoizing per-property CMA lookups, comp-sample loads, each listing's `Exposure` (and its group's episode rows), and `exposure.area_median_dom` (a city-level aggregate identical for every row — keyed on `as_of`, and cached by membership since `None` is a real answer). Any new call site must pass `cache` through: without it that one aggregate re-queried 2-3x per listing and was ~63% of the request.

## Tracker (`api/tracker.py`)
- `GET /api/tracker` → `[{id, stage, notes, my_max_bid, disclosure_checklist, offer_due_at, deal_id, cma_estimate, overbid_point, listing: ListingSummary}]` in creation order; `cma_estimate` is the latest CMA, `overbid_point` the blended `predicted_sale.point` (null without a model), and `listing` carries `predicted_sale`/posture.
- `POST /api/tracker` body `{listing_id}` → `{id, stage}` (idempotent: an already-tracked listing returns its existing row; 404 on an unknown listing) / `DELETE /api/tracker/{id}` → `{deleted}` (alerts that cite the row keep their `listing_id` and lose `tracked_listing_id`). Creating a row also watches the home (stamps `properties.watched_at`), so a later `DELETE` leaves it on the Watchlist.
- `PATCH /api/tracker/{id}` body `{stage?, notes?, my_max_bid?, disclosure_checklist?}` (partial checklist merge) → `{id, stage, notes, my_max_bid, disclosure_checklist}`; 422 on an unknown stage. Stages are `saved|toured|disclosures|offer_prep|offered|won|closing|lost|passed`; the `GET` payload carries `deal_id` (null until a deal exists) so the kanban can hand off to `/closing`.

## Watchlist (`api/watchlist.py`, `hb/watchlist.py`)
Every home with `properties.watched_at` set — the Watch button, creating a tracker row, or logging a tour — until the buyer removes it (04 §properties `watched_at`). Keyed on the **property**, so a relisted home (a new `listings` row) stays the same entry.
- `GET /api/watchlist` → `{last_seen_at, items: [...]}`, items most recently changed first. Each item is the `ListingSummary` of the property's **current** episode (latest `list_date`, then `first_seen`) plus:
  - `status` — the episode's status, except `sold` when the cached Realtor history has a `Sold` entry dated on/after the episode's `list_date` (the home sold after leaving the market; 05 §11).
  - `sold_price`, `sold_date`, `sold_source` (`listing` = the scan saw it close | `public_record` = from the Realtor history | null).
  - `sp_lp` — sold price ÷ original ask (null until sold); `vs_max_bid` — sold price − the tracker's `my_max_bid` (positive = it went for more than the buyer would have paid; null without both).
  - `involvement` — `{tracked_id, stage, my_max_bid, tour_count, last_toured_on, verdict, gut_score}` (the most recently updated tracker row across the property's listings; the latest tour).
  - `last_change` — the newest `listing_events` row across the property's listings (`{event_type, old_value, new_value, observed_at}`), or null; homes without one sort last.
  - `watched_at` — when the home went on the Watchlist (the page's **Recently added** sort).
  - `last_seen_at` is the `settings` row `watchlist_seen` (null before the first visit).
- `POST /api/watchlist/seen` → `{previous, at}` — stamps the visit; the page calls it once per open, after reading `last_seen_at`.
- `PATCH /api/watchlist/{property_id}` body `{watching: bool}` → `{property_id, watching}`; 404 on an unknown property. `true` stamps `watched_at` (kept if already set); `false` clears it — the home leaves the list even if it was toured (its tours and tracker rows are kept; a new tour, tracking it or `true` puts it back). Removing also drops the home from Watchlist alert scope (09 §2); a home still in an active tracker stage keeps its tracker alerts.

## Prep — Get Ready checklist (`api/prep.py`, docs/15)
- `GET /api/prep` → `{phases: [PrepPhase], rollup}`. No parameters and no row required — state is the `settings` row `prep_checklist`, absent until first write.
- `PATCH /api/prep` body `{checklist: {task_key: {done_on?, note?} | null}}` → same shape. Merges at both levels like the deal and tour checklists; `null` for a task key deletes that entry. **422 on an unknown task key** — the keys are the storage contract, so a typo must not silently persist.

`PrepPhase = {key, title, blurb, tasks: [PrepTask]}`;
`PrepTask = {key, label, phase, owner, why, how, needed_by, lead_time, done_on, done, note}`.
`rollup = {total, done, long_lead_open[], before_tour_open[], before_offer_open[], next_action, phases: [{key,title,total,done}]}`.

No dates: there is no acceptance to count from. Ordering comes from `lead_time` — the tasks gated by calendar time regardless of effort — which is what `long_lead_open` surfaces.

## Deals — closing tracker (`api/deals.py`, docs/14)
- `GET /api/deals/spec?listing_id=&accepted_on=&close_of_escrow_on=&investigation_days=&appraisal_days=&loan_days=` → `{phases: [ClosingPhase], anchors, contingency: {investigation_days, appraisal_days, loan_days, emd_business_days, label}}` (omitted day-counts default to the pack's; `accepted_on` defaults to today and `close_of_escrow_on` to acceptance + 30 days). **Preview with no deal row** — lets the closing page show the process before an offer is accepted, which is when it should first be read. Declared before `/{deal_id}` so the static path is not captured by it.
- `GET /api/deals?status=` → `[Deal]`, newest acceptance first (no `spec`/`contacts`)
- `POST /api/deals` body `{listing_id, accepted_on?, purchase_price?, close_of_escrow_on?}` → `Deal`. **Idempotent on `listing_id`**. `accepted_on` defaults to today, `purchase_price` to the listing's list price, and the contingency counts to the pack's defaults (**17 / 17 / 21** plus 3 business days for the EMD under the `ca` pack; 10 / 21 / 21 under the `us` base). Moves the listing's tracked row to stage `closing` if one exists.
- `GET /api/deals/{id}` → `Deal` with `spec` and `contacts` attached
- `PATCH /api/deals/{id}` body `{accepted_on?, purchase_price?, emd_amount?, emd_sent_on?, close_of_escrow_on?, investigation_days?, appraisal_days?, loan_days?, financed?, escrow_company?, escrow_number?, status?, notes?, checklist?, waive?}` → `Deal`. Scalars overwrite; `checklist` **merges** at both levels (task key, then the fields within a task entry) like `property_tours.checklist`. **`waive: ["investigation"|"appraisal"|"loan"]`** is the only way to clear a contingency day-count — `None` in a patch body already means "not supplied", so NULL (= waived) cannot be expressed positionally. 422 on a bad status, non-ISO date, or unknown waive name.
- `DELETE /api/deals/{id}` → `{deleted}` (cascades to the deal's own `deal_id` contacts; contacts saved on the listing survive)
- `GET|POST /api/deals/{id}/contacts`, `PATCH|DELETE /api/deals/{id}/contacts/{contact_id}` — the deal team, stored in `contacts` with `deal_id` set. **The team also includes the listing's own contacts** (`listing_id = deal.listing_id`, saved on the detail page before the offer): GET lists them, and PATCH/DELETE accept them, so the closing page's remove button works on every row it shows. Same body, `Contact` shape and `kind` vocabulary as the listing routes (§Listings; `hb/api/contacts.py`).

`Deal = {deals row fields + address, city, zip, year_built, rollup, spec?, contacts?}`.
`ClosingPhase = {key, title, blurb, tasks: [ClosingTask]}`;
`ClosingTask = {key, label, phase, owner, why, how, form, blocking, anchor, offset, due_on, due_overridden, cost, cost_band, done_on, done, waived, note}`.
`rollup = {anchors: {acceptance, emd, investigation_removal, appraisal_removal, loan_removal, coe}, waived: [anchor], total, done, overdue[], due_soon[], blocking_open[], next_action, phases: [{key,title,total,done}], days_to_close, costs: {year, label, low, high, items[]}}`.

Every `due_on` and the whole `rollup` are **recomputed on read** by `hb.closing_spec` from the deal's five contract numbers — never stored — so correcting `accepted_on` re-dates the transaction and a spec correction reprices an open deal. A waived contingency's anchor resolves to null and **every task hanging off it disappears from `spec` and `rollup`**, rather than being shown greyed out.

## Tours (`api/tours.py`)
- `GET /api/tours/checklist?listing_id=|property_id=` → `{property_id, facts: {year_built, sqft, assessor_sqft, sqft_mismatch, hazards[]}, sections: [{key, title, blurb, items: [Item]}], agent_questions: [string], context_notes: [string], costs: {year, label}, photo_shot_list: [{key, label, shot}]}` where `Item = {key, label, type: 'bool'|'number'|'text'|'choice'|'rating', choices[], hint, photo, flag_when, cost, cost_band: {key, label, low, high}|null}`. The spec is pruned per home (`applies_when`, e.g. cripple-wall items only pre-1980). `flag_when` ships to the client deliberately so the tour panel and the Field page raise red flags as you type, without a round trip (the interpreter is `frontend/src/lib/tourFlags.ts`, mirroring `tour_spec.evaluate`). Items, agent questions, age notes and cost bands are the current pack's (`hb/packs/<key>/tour.py`, `docs/packs/README.md`); `costs` carries the cost book's year and label for the UI.
- `GET /api/tours?listing_id=|property_id=` → `[Tour]`, newest visit first
- `POST /api/tours` body `{listing_id?, property_id?, toured_on?, kind?}` → `Tour`. Idempotent on `(property_id, toured_on)`; `toured_on` defaults to today. Creating a tour watches the home (`properties.watched_at`, 07 §Watchlist); the import below does the same for each row it creates.
- `PATCH /api/tours/{id}` body `{kind?, checklist?, agent_answers?, gut_score?, verdict?, notes?, repair_low?, repair_high?}` → `Tour` (JSON fields **merge**, like `tracked_listings.disclosure_checklist`)
- `DELETE /api/tours/{id}` → `{deleted}`

`Tour = {id, property_id, listing_id, toured_on, kind, checklist, agent_answers, gut_score, verdict, notes, repair_low, repair_high, source, created_at, updated_at, flags: [{key, label, value, section, cost}], costs: {low, high, items[], overridden}, unanswered: [{key, label, section}]}`. `flags`/`costs`/`unanswered` are recomputed on every read by `hb.tour_spec.evaluate()` — never stored — so no client reimplements the rules.

- `GET /api/tours/field-data?listing_ids=a,b,c` → `{generated_at, homes: [FieldHome]}`. The seed the Field page (`/field`, docs/08 §11) loads for the day's homes in one call. Each `FieldHome` is the full `_field_home()` payload — facts, pricing, CMA estimate + predicted range, the age-pruned `spec` (carrying `flag_when` so flags raise with no round trip), and any tour already recorded (`existing`). 404 on an unknown listing, 422 on empty ids.
- `POST /api/tours/import` body `{tours: [{property_id?, listing_id?, toured_on, kind?, checklist?, agent_answers?, gut_score?, verdict?, notes?}]}` → `{created, updated, unchanged, conflicts: [{property_id, toured_on, field, existing, incoming}], errors: [{property_id, toured_on, error}]}`. **JSON only** — the Field page's **Copy answers** recovery path (docs/08 §11), for when its normal `POST`→`PATCH` save could not run. **Gap-fill only**, deliberately unlike the sync `PATCH` (which overwrites): an incoming value is taken only where the app holds nothing, and a genuine disagreement is reported under `conflicts` rather than applied — so replaying a stale backup can never revert an in-app edit, and a re-import is a true no-op (`unchanged`). 422 when no tour is supplied. Imported rows carry `source: 'offline_kit'`.

## Offer & affordability (`api/affordability.py`)
- `GET /api/profile` / `PUT /api/profile` → buyer_profile row
- `POST /api/affordability/calc` body `{price, city?, down_payment? (dollars), rate?, hoa_monthly?, include_earthquake_ins?}` → `{piti, breakdown: {pi, tax, insurance, pmi, hoa, earthquake}, closing_est, cash_needed, supplemental_tax_note, reserves_after, reserves_ok, rate_used, tax_rate_used, payment_limit (null without income), payment_ok}`
- `POST /api/offer/solve` body `{listing_id?, city?, overrides?: {cash_available?, down_payment?, rate_assumption?, appraisal_gap_tolerance_pct?, insurance_monthly_est?, include_earthquake_ins?, hoa_monthly?}}` (the only override keys; `annual_income` and `monthly_debts` always come from the profile, and `hoa_monthly` defaults to the listing's `raw.hoa_fee`) → `{max_defensible_bid, cma_estimate, predicted: {low, point, high, basis, unadjusted_point, rejection_weight}, verdict: string, verdict_template, escalation_cap, gap_capped, ltv_capped, payment_capped, limits: {cash, down_payment, payment|null}, e_basis: 'adjusted_blend'|'cma'|'list'|'none', recommendation: 'underbid'|'at_list'|'overbid'|null, opening_range: {low, high}|null, ceiling, posture: {the `posture_detail` shape minus adjusted/unadjusted_point}|null, confidence}`. `max_defensible_bid` is the lowest of the three limits in `limits` (06 §6): the **cash/appraisal-gap-constrained** max (what you *can* pay, E = the market-adjusted blend); `ceiling` is the posture-driven value-justified cap (what you *should* stop at — for a lingering listing `min(list, 1.02 × adjusted point)`, and the opening never exceeds it) and **`escalation_cap = ceiling`**. `listing_id` omitted ⇒ profile-only inverse readout: the lowest of the reserves-based cash limit (cash covers down + closing + 6 months of PITI), the 20%-down floor and the income payment limit (`city` supplies the tax rate).

## Config (`api/config.py`)
- `GET /api/config` → `{geography: {name, state, timezone, cities: [{name, county, zips[], flags[]}], zips[], counties: [{name, assessor_label, assessor_url, effective_tax_rate}], map: {center: [lon, lat], zoom}, price_band: {min, max}}, pack: {key, label, contingency: {investigation_days, appraisal_days, loan_days, emd_business_days, label}, costs: {year, label}, hazards: [{key, label, tone}], rating_sources: [{key, label, blurb}], tracker_checklist: [{key, label, kind}], affordability: {earthquake_monthly_default, optional_insurance_label}, attorney_phrase, guide: {available}}}`. Static for the life of the process (the UI caches it with `staleTime: Infinity`, prefetched by the layout). Everything the frontend knows about the geography and the state pack — city lists, map centre, assessor links, contingency defaults, hazard and rating labels, the Tracker checklist fields — comes from here, never from literals (02 §3). `tone` is a fixed colour-family vocabulary (`sky|orange|amber|purple|rose|slate`) because Tailwind cannot see class names that arrive from an API.

## Guide (`api/guide.py`)
- `GET /api/guide/closing` → `{pack, pack_label, doc, title, intro_md, sections: [{id, n, title, markdown}], phase_map: {phase_key: [{id, label}]}}` — the pack's closing playbook (`docs/14-closing-playbook.md` for `ca`) read from disk at request time and split on its `## N.` headings; stable section ids, the hidden sections (§15, written for developers) and the per-phase links come from the pack's `Guide` record. **404** when the pack ships no guide (the `us` base), which the Closing page renders as a one-line note.
