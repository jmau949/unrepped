# 08 — UI Spec

Vite + React + TS SPA. TanStack Router pages, TanStack Query for data, Tailwind, Recharts, MapLibre GL. The shell is exactly one viewport tall (`h-dvh`) and `main` is the scroll container, so split views can size themselves with `h-full` — with a page-level scroll their map grows to the full table height and runs thousands of pixels past the fold, which makes "what the map is showing" meaningless. Left sidebar nav with the 14 entries of `NAV` in `components/Layout.tsx` — Dashboard, Get Ready, Listings, Open Houses, Recently Sold, Tracker, Watchlist, Closing, Field, Compare, Affordability, Alerts, Supply, Data Log (the CMA workbench is embedded in listing detail, not a standalone nav page); top bar shows `db: <status>` and data freshness (`/api/ops/health`: last scan time, and the RentCast quota only when a `RENTCAST_API_KEY` is set) and an `alerts: N` pill linking to `/alerts`: the count of alerts no channel has delivered yet (`GET /api/alerts?undelivered_only=true`, refetched every 60 s, `100+` past the page size, amber when non-zero); acknowledging one on the Alerts page refreshes it. When `scan_overdue_since` is set, a red `scans stale since <local time>` pill shows at every width (the other freshness fields hide on phones) — a missed scan otherwise looks exactly like a quiet market. Responsive: usable on a phone (single-column stacking), optimized for desktop. Below `lg` the split views (Listings, Recently Sold, Open Houses) drop `h-full` and the page scrolls in `main` instead: the list keeps its own scroll box capped at `70dvh` (Open Houses' scroll restore and the Listings map-hover `scrollIntoView` both need that scroller), and the map follows at a fixed `h-72` (`MapView`'s floor is `16rem` on phones, `24rem` from `lg`) — on Open Houses after the schedule panel, which is capped at `50dvh`. Squeezing both halves into one viewport left a phone with the map and about one row. On phones Recently Sold hides its List, $/sqft and Sold date columns (the date moves under the sold price), the Listings price cell and the Open House price/badge column wrap their badges, and Open House rows drop the thumbnail. The stacked grid is `grid-cols-1` (`minmax(0,1fr)`) so a long one-line slot description cannot widen the column past the screen. **Code splitting**: every page is a lazy route chunk (`lazyRouteComponent` in `router.tsx`; only `Layout` is eager) and the two map components are lazy behind a `Suspense` skeleton — `LazyMapView` on Listings/Recently Sold/Open Houses, `CmaMap` inside the CMA workbench. `maplibre-gl` alone is ~1MB, so loading it eagerly held up every table on the LAN; it now streams in beside rows that are already usable. The server sends assets uncompressed, so these are raw wire bytes. Router `defaultPendingComponent` covers the in-flight chunk. Loading states = skeletons; every chart/table has an empty state naming the pipeline that fills it (e.g. "No data yet — run `hb pipeline daily`").

Shared components: `MetricTile` (value + 90d delta arrow + sparkline), `ListingBadges` (price reduction — `↓ <cut_pct>%` with `×N` when more than one cut was observed, SOLD, PENDING, RELIST, CDOM vs source DOM, predicted-sale chip, green `Open Sat 1–4 PM` chip from `next_open_house` — hidden via `hideOpenHouse` on the Open Houses page, which shows the slot itself), `AvmSpreadBar`, `AdjustmentGrid`, `OverbidHistogram`, `VerdictCard`, `MapView` (MapLibre, OSM tiles, pin popovers → listing links; pin labels carry the sold price on closed sales and the list price otherwise, and it reports marker hover + its viewport back to the page via `onHover` / `onBoundsChange`, refitting to every pin when `refitKey` changes; optional `pinLabel` replaces the price label — Open Houses pins show the slot's weekday and start time — and optional `home` adds a green Home pin included in the fit).

## 1. Dashboard (`/`) — the "learn the market" page
- A **Focus ZIP** `<select>` (one option per target ZIP, `94402 — San Mateo`, the first by default) driving one row of `MetricTile`s (from `/api/market/summary`): median sale price, $/sqft, **sale-to-list** (`avg_sp_lp`, rendered as a percent), median DOM, inventory, months supply — each with 90-day delta and 12-month sparkline. The page header carries a dark **Shopping band** chip (`Shopping band: $2.0M – $3.0M`, the summary's `target_band`).
- ZIP comparison table (same metrics as sortable columns; row click → filtered Listings page).
- Rate chart: MORTGAGE30US 24 months (`/api/market/rates`).
- Time-series explorer: geo + metric pickers → line chart (`/api/market/series`), compare up to 4 geos.
- Footer: "Pipeline freshness" table of the last 20 pipeline runs (`/api/ops/pipeline-runs`, newest first): job, status coloured by status (ok green / noop gray / partial amber / failed red / running blue), finished time, items seen, truncated error.

## 2. Listings (`/listings`)
- **Search box** (leading the filter bar): free text over address / city / unit / ZIP-prefix, debounced 250ms and sent as `q` — each keystroke would otherwise re-run the server-side per-row prediction pass. While a search is active the *default* target band is suppressed (an explicitly typed price range still applies, and the band chip hides), because a search is a hunt for one specific home and the band would silently hide it.
- Filter bar: status (**defaults to active + pending** — matches Redfin's default; pending rows carry an orange PENDING badge), city multi-select, ZIP, price range (**defaults to the geography's `[price_band]`, clearable to see everything**; two `MoneyInput` boxes that show thousands separators, `2,000,000`, and apply as you type), beds, **price-reduction select** (any price move / reduced / ≥3% / ≥5% / ≥10% — one control driving `has_price_cut` for "any" and `min_cut_pct` for the thresholds), "stale only" (CDOM > 1.5× area median), sort (newest / price / days on market / biggest reduction).
- Split view: table (thumbnail, address, **price — sold rows show the SOLD price bold with `ask <original> ±% · <sold date>` beneath it, everything else shows the list price**, beds/baths/sqft, list date, **CDOM (source DOM struck through when they differ)**, badges, predicted-sale chip) ↔ `MapView`; **hover syncs both ways** — a hovered row reddens its pin, and a hovered pin tints its row blue with a left accent bar and scrolls it into view (only map-driven hover scrolls, or running down the rows would fight the scroll position).
- **The table lists only what the map is showing.** `MapView` keeps the whole result set — it is the thing being panned — and the table filters to the reported viewport; filtering the map's own input instead would loop (fewer pins → refit → tighter bounds → fewer pins). A stale viewport is dropped the moment the result-set id list changes, keyed exactly as `MapView` keys its refit, so the map's fly-to does not briefly empty the table while a background refetch leaves the user's pan alone. A home with no coordinates is on no map and stays listed. When anything is off-screen the header shows `N in view · M off-screen — reset map`, the button re-fitting the map around every pin.
- Row actions: track/untrack (star), open detail.

## 2b. Recently Sold (`/sold`)
Closed sales as a shopping-research feed, from `GET /api/listings?status=sold` sorted newest-sold-first.
- Filter bar: city, ZIP, **sold-price range defaulting to the target band** (chip `band $2.0M–$3.0M ✕`, clearable — filters on SOLD price, not list; comma-formatted `MoneyInput` boxes that apply as you type), sort (newest sold / sold price / DOM).
- Split view like §2: table (thumbnail, address, list price, sold price, sold $/sqft, Δ vs original ask red/green, sold date) ↔ `MapView`, hover sync; row click opens the detail page in a new tab.
- **Viewed indicators** (unread-mail pattern): `viewed_at = null` rows carry a solid blue dot before the address; viewed rows are dimmed (muted text, half-opacity photo) with a gray ✓ (hover = view date). Header shows an `N not yet viewed` chip. A row is viewed once its **detail page has been opened while it is sold** (stamped server-side by `GET /api/listings/{id}`; the row also flips optimistically on click since the list query is cached). Opening a home while it is still on the market does not count — `listing-scan` clears `viewed_at` on the transition to sold (05 §4.3), because the sale price is the thing the sold feed exists to show. Rationale: closings are reported late (median ~2 days after sale, tail to 30 — the scan re-pulls a rolling 30-day sold window daily), so new rows keep appearing *behind* already-reviewed dates; the dot makes stragglers obvious without re-reading the whole list.

## 3. Listing detail (`/listings/:id`) — the money page
Layout top-to-bottom:
1. **Header**: photo gallery — primary image + thumbnail strip over the full downloaded set (from `/photos`), with a full-screen lightbox that pages through all photos (full-height edge click zones — a near-miss on a chevron navigates rather than closing — plus arrow keys, touch swipe, and an explicit × / Esc / backdrop-click to close); address, list price with **`PostureBadge`** (docs/06 §5.6 — the calibrated share stated as a number, with no confidence adjective: amber "bid floor — ~7 in 10 such homes sell at or above asking (typ. 5.5% over)" only when classified underpriced; slate "market-tested — ~5 in 10 sell below asking, ~5 in 10 at or above"; red "lingering — ~7 in 10 such homes sell below asking (typ. 2.7% under)"; grey "pricing posture unknown — no exposure data"; the tooltip opens with the plain-language meaning for this home (`postureExplanation`, shared with the posture panel) and then lists the signals), beds/baths/sqft/lot/year, condition-tag editor (writes `PATCH /api/properties/:id`), **tracker control**, source link, offer-date field (auto-suggest list_date+7, shows countdown).
1b. **Tracker control** (header control row, beside condition/offer-date): when the home is not tracked it is an explicit `★ Add to tracker` button (`POST /api/tracker`, which starts the row at `saved`); once tracked it becomes an amber `★ Tracking [stage ▾] board ↗ ✕` group — the stage `<select>` writes `PATCH /api/tracker/:id` over the full stage vocabulary (§5), `board ↗` links to `/tracker`, `✕` untracks. Bound to `tracked_id` + `tracked_stage` on the detail payload; both mutations invalidate the `listings` and `tracked` queries so the Listings star column and the kanban stay in step. Rationale: adding a home to the pipeline is a decision made *while reading the detail page*, and an unlabelled star neither said it was possible nor showed which stage the home was already at. Next to it, the **Watch control**: a sky-blue `👁 Watch` button when the home is not on the Watchlist (§5b), else a `👁 Watching list ↗ ✕` group; both write `PATCH /api/watchlist/:property_id {watching}`, bound to `watching` on the detail payload, and invalidate the `watchlist` query. It is how a buyer follows a home's outcome without tracking or touring it — tracking already watches it (07 §Tracker).
1c. **Contact the listing side** (`ContactPanel`, the first card under the header — who to call before what it is worth): the listing agent, office, broker and MLS id from `listing_contact` on the detail payload (the MLS record the scan already stores; 07 §Listings), rendered as direct `tel:` links per phone with its type, a `Text ↗` `sms:` link for mobile lines, a `mailto:` link on the listing's email that opens with the subject and body prefilled, and Copy buttons (the clipboard API needs a secure context and the LAN server is plain http, so the fallback selects the text in an off-screen textarea and runs `execCommand("copy")`). The card carries contact details only — plain `tel:` and `mailto:` links, no prefilled message; what to say is the buyer's own (14 §2.3). Below them, **contacts saved on this listing** (`GET|POST|PATCH|DELETE /api/listings/:id/contacts`, kinds shared with the deal team plus `owner`): a table of kind · name · company · phone · email · notes with remove, and an add form; and one line of **free owner-of-record links** — one per `geography.counties[]` entry that carries an `assessor_url`, labelled by its `assessor_label` (else `<name> Assessor`), read from `GET /api/config`; every such county is linked, since properties carry no county, and the line is omitted when no county has a URL — with the instruction to save the name as an `owner` contact. Empty state when `listing_contact` is null (Realtor drops the advertiser block on ~1 in 4 listings): "No agent on the source record for this listing. Add one by hand below, or look up the owner of record." Rationale: the only other route to the agent is the portal's contact form, which assigns a *buyer's* agent and a representation agreement with a fee — the one thing an unrepresented buyer must not do by accident — and the direct line was already sitting unread in `listings.raw`.
1d. **Open houses** (header column, under the control row; only when `open_houses` on the detail payload is non-empty): a green-bordered block listing **every** upcoming slot for the home, soonest first — the `ListingBadges` chip carries only the soonest window and no text. Each row: the window (`Sat 1–4 PM`, rendered in the payload's `timezone`, not the device's), a violet `virtual` tag when the slot has that method, the source's **description in full** (the agent's note on the slot — "This is a Twilight Tour!", host name, "offers reviewed Tuesday" — which the Open Houses page truncates to one line), `Event link ↗` when the source gave one, and the same `+ Schedule` / `✓ Scheduled` toggle as §14 (`PUT|DELETE /api/open-houses/:id/schedule`; invalidates the `listing`, `open-houses` and `open-house-schedule` queries so all three views agree). A cancelled slot (one the buyer had scheduled and the source then dropped) stays, struck through in red with "cancelled — no longer listed by the source" and no toggle. Header link `all open houses ↗` → `/open-houses`. Rationale: the slot note is often the only place the agent says *how* the showing works (twilight tour, appointment-only, neighborhood event), and that was reachable only by finding the home again on the Open Houses list.
1e. **Listing remarks** (card between Contact and Timeline; only when `remarks` is non-null): the listing agent's public remarks verbatim from the source record (`listings.raw.text`, 05 §4.2), line breaks preserved, with a one-line footnote that it is a sales pitch rather than a disclosure and that the condition tag and offer date are parsed from it (05 §4.7). Rationale: every portal shows the description under the photos; the app already stored it for the parsers and never displayed it.
2. **Timeline**: Realtor.com sale/listing price history (from `property.price_history` in the detail payload — populated in the DB by the `price-history` scrape, never fetched on view) **merged with the app's own observed episodes** (`listing_group.episodes` → Listed/Relisted/Delisted/Pending/Sold rows with true dates, plus observed `price_change` events). The Listed/Relisted price is the episode's `original_list_price` — the live list price would make that row rewrite itself on every cut, so a home listed at $2.399M and cut to $2.35M would read "Listed $2.35M" directly above "Price change $2.399M → $2.35M" — Realtor scrubs withdrawn listings from its history, so app-observed rows win same-event collisions. Newest-first rows of date · event · price · $/sqft, plus a "Built {year}" row. Raw `listing_events` are the fallback only when no stitched group exists; keeps the multi-episode cumulative-DOM note.
2b. **Pricing posture panel** ("Pricing posture — will this sell below asking?"), written to be read without the spec: the badge (plus the estimate-divergence chip when sources disagree); the headline ("**78%** of homes with this exposure history sold below their asking price; the typical one closed at **97.3%** of ask. Separately, about **24%** of listings this far past the area median are withdrawn rather than sold — the percentage above counts only the ones that did sell", the withdrawal sentence only past 2× the median); a plain-language paragraph for this home's posture (`postureExplanation`: lingering ⇒ "…longer than the typical home here takes to go pending (about 13 days), and nobody has taken it at this price… about 7 in 10 sold for less than asking… a probability, not a verdict: about 3 in 10 still sold at or above"; early ⇒ "…the asking price is best read as a floor for bidding, not a cap… if it is still active a couple of weeks from now, that picture changes"; market-tested ⇒ "…split close to even… the market has not made up its mind"); **The evidence**: an exposure sentence ("Episode 2 of this campaign: 20 days at the current asking price, 50 days cumulative… The typical home in this area goes pending in 13 days, so this one is at 1.5× that"), then one row per signal — log-odds points (positive/red is evidence the ask comes down, negative/green that it clears) + the backend detail + a muted why-line (`SIGNAL_WHY`: exposure carries nearly all the weight; a cut adds little once exposure is counted; a relist restarts the clock; a passed offer date is live-only) — and a how-to-read footnote (rows add up to the probability; weights fitted on this area's own sales and re-checked by every golden backtest, so "7 in 10" means 7 in 10 past listings in that situation really did sell below asking); **Deliberately not counted**: the value-gap sentence ("The asking price sits 9.6% below the model's own value estimate") followed by why value estimates do not feed the probability; and, when `rejection_weight > 0`, the red explanation of why the predicted sale price at the top is lower than the model's estimate ("the model on its own valued this home at $2.93M, but exposure past the area median says the market is not paying $2.65M, so the served value is pulled toward 98% of asking (weight 1.00 of 1.00), giving $2.60M — lingering homes here really do close near asking, so this is the number to anchor an offer on"). The panel renders for `unknown` too, with the no-exposure-data explanation and any cut/relist facts.
3. **Overbid panel**: `OverbidHistogram` of SP/LP weights, predicted range banner ("Likely sale $2.15M–$2.39M — median 112% of list, n=14"), fresh/stale basis + reason, pre-adjustment note when the posture layer pulled the served value lower, atypical-pricing flag.
4. **CMA workbench**: the full comparative-market-analysis tool embedded inline — estimate ± range + confidence chip + reasons, run-history dropdown, "re-run fresh", comp map, editable `AdjustmentGrid`, and candidate drawer (see §4 for the panel anatomy). Auto-runs on first view so an estimate is present without a separate trip.
5. **AVM spread**: `AvmSpreadBar` with own_cma / realtor_estimate / rentcast (/zestimate) dots on one axis, spread verdict line, "Refresh estimates" button (`POST /enrich`; shows the RentCast quota when RentCast is configured).
6. **Affordability card**: PITI breakdown at list, at CMA estimate, and at overbid p50 (`POST /affordability/calc` ×3); reserves warning.
6b. **Schools**: assigned elementary/middle/high for the home (from `property.schools[]`) — matched by **school-district boundary** (point-in-polygon, `school-districts` pipeline + `hb/schools_match.py`), then nearest non-charter school within that district per level; rows that fell back to plain-nearest or ZIP matching carry a small `nearest`/`zip` marker (docs/05 §12). One row per school with one badge per rating source in `ratings[]` (green 8–10 / amber 5–7 / red 1–4), the pack's primary source first — **CAASPP** (state test-score decile, `school-ratings` pipeline) under the `ca` pack, SchoolDigger elsewhere — each labelled with its source (hover for the native label), plus level and distance; empty until the `schools` pipeline runs. Source labels and the footer's one-line explanation of each come from `GET /api/config` → `pack.rating_sources`; a school with no snapshot shows "—". Footnote: private schools not included.
6c. **Tour log** (`TourPanel`, docs/13): collapsible checklist pruned to this home's age, with a per-section red-flag count; gut score 1–5, verdict, kind, notes; per-item photo shot-list ticks; agent Q&A. Footer rolls flagged defects into a **deferred-maintenance** table and a **condition-adjusted value** line against the latest CMA estimate, with a low/high override for real quotes. Multiple visits per home select via a dropdown. Placed *before* the offer helper — observations should inform the recommendation, not trail it. Empty state: “No tour recorded yet. Start one here, or capture it in Field mode — the checklist is pruned to this home's age, so work down it while you are standing in the house.” The header control row also carries **Copy deep-dive brief** (`GET /api/listings/{id}/brief`), which falls back to a file download because `navigator.clipboard` needs a secure context and the LAN server is plain http.
7. **Offer helper**: `VerdictCard` from `POST /offer/solve` — **recommendation pill (UNDERBID / BID AT LIST / OVERBID) with confidence** (the confidence word's tooltip explains the tiers: high at an 80% share, medium at 65%, capped at medium when value estimates disagree) and a one-sentence meaning under the pill (underbid: "Open below asking and stop at the ceiling… the ceiling is the most the evidence justifies, however much cash you have"; at list: "…past listings at this stage split close to even, so the model value, not the asking price, sets the ceiling"; overbid: "Expect competition… the asking price is a floor for bidding; the ceiling is the top of the likely sale range"), suggested opening range, the value-justified **ceiling** as the headline number (escalation cap = ceiling; "Set ceiling as my max bid" writes it to the tracker), cash ceiling (max defensible bid) as the secondary line, a footnote distinguishing opening / ceiling / escalation cap / cash ceiling, binding-constraint notes (20%-down floor, income payment limit; an amber note when no income is entered, since the cash ceiling then ignores the monthly payment), estimate-divergence hedge, plain-language verdict.
8. **Context**: hazard flags row — one chip per pack hazard layer (flood everywhere; the `ca` pack adds wildfire / liquefaction / fault zone), label and colour tone from `GET /api/config` → `pack.hazards` — and a sqft-mismatch warning banner if `sqft_mismatch`.

## 4. CMA Workbench (embedded in listing detail §3, keyed by `propertyId`)
Rendered inline on the listing-detail page (there is no `/cma` route or nav tab). Backed by the same `/api/cma/*` endpoints.
- Left: comp map (subject pin + numbered comp pins, 0.5/1.0 mi radius circles).
- Right: `AdjustmentGrid` — one column per comp, rows: sale price, sale date, time adj, sqft adj, baths, lot, condition, **adjusted price**, similarity, include-toggle. Cells editable for overrides (`PATCH /cma/runs/:id/adjustments`); edits and toggles recompute live (new run).
- Header: estimate + range + confidence with reasons; run-history dropdown (`GET /cma/runs`); "re-run fresh" button.
- Candidate drawer: next-best excluded candidates with scores, one-click swap in.

## 5. Tracker (`/tracker`)
- Kanban columns = stages (saved → toured → disclosures → offer_prep → offered → won → closing / lost / passed); drag between columns (`PATCH /tracker/:id`). The stage list is `TRACKER_STAGES` in `frontend/src/api/client.ts`, shared with the detail page's tracker control (§3 item 1b) and mirroring `STAGES` in `api/tracker.py`, which 422s on anything else.
- Homes arrive here from the Listings star column, or from `★ Add to tracker` on a listing detail page; the empty state names both.
- Card: listing photo (`listing.photo_url`, the first photo; a slate placeholder when none — the image is not itself draggable, so dragging it moves the card), address, list price, predicted p50, listing-status pill, offer-date countdown (red < 3 days), CDOM badge, my_max_bid. Cards in `won`/`closing` also carry a **"Start closing tracker →" / "Closing tracker →"** link to `/closing` (§12), which carries a won home through to close.
- **Listing status** (`listing.status`) is a pill in every card's badge row: For sale (`active`, emerald) / Pending (orange) / Sold (slate) / Off market (`delisted`, grey). Labels and colours live in `frontend/src/lib/status.ts`, shared with the Watchlist rows (§5b). **Sold homes** also show `sold <sold_price> on <sold_date>` in place of the predicted p50 — a tracked home can sell to someone else while it sits in `saved`/`offered`, and the board must say so rather than keep showing a prediction for a home that is gone.
- Card detail drawer: notes, disclosure checklist (fields from `GET /api/config` → `pack.tracker_checklist`; under the `ca` pack: packet received / TDS-SPQ read / pest §1 total $ / NHD read / HOA docs / insurance quoted), my_max_bid field. The header repeats the status pill, with sold price and date for a sold home.

## 5b. Watchlist (`/watchlist`) — what happened to the homes you looked at
The Tracker answers "where am I with this home?"; the Watchlist answers "what did it do after I looked?" — so a buyer who passes, loses, or pauses the whole search still learns what each home sold for. Same homes, different question, which is why it is a separate page and not more Tracker columns. Nav item sits directly under Tracker.

- **Membership** (07 §Watchlist): every home the buyer watched (`👁 Watch` on the detail page, §3 1b), added to the tracker (which watches it, so untracking later keeps it here), or toured (logging a tour watches it), until the buyer removes it. The empty state names all three ways in and says homes stay whatever the buyer decides.
- Header: title, one-sentence explanation linking to `/tracker`, and a blue **"N changed since your last visit"** pill. "Changed" = the row's `last_change.observed_at` is after `last_seen_at` as it stood when the page opened; the page then calls `POST /api/watchlist/seen` once, keeping the opening stamp in state so a background refetch does not clear the highlights mid-visit. First visit highlights nothing.
- **Status tabs** with counts: All · For sale (`active`) · Pending · Sold · Off market (`delisted` — the buyer-facing word). Beside them, a two-way sort toggle: **Recently added** (default — newest `watched_at` first, sorted client-side) or **Latest change** (the API order, newest `last_change.observed_at` first, homes with no event last, so whatever just moved is on top). Tabs filter without changing the order.
- **Row** (a stacked list, not a table, so it reads on a phone): photo + address link to the listing detail page, a status pill, and three lines —
  1. **The story**, one plain sentence built client-side from the row: *"Sold Oct 5 for $1.62M, +4.0% vs the original $1.56M ask"* (with *"after it left the market (public record)"* when `sold_source='public_record'`); *"Under contract after 21 days, cut 2× to $1.45M (−6.5%) first"*; *"For sale, cut to $1.45M (−6.5%) · 34 days on market"*; *"Taken off the market — watching for a relist or a quiet sale"*. Days are cumulative DOM when the home relisted.
  2. **Your involvement**: *"Toured Aug 3 (2×) · verdict: pass · gut 3/5 · Tracker: passed · your max $1.50M"* — why the home is on the list.
  3. Facts + last change: city, ZIP, beds/baths, sqft, *"last change: Price change Oct 20"*.
  Right column: the price (sold price once sold, else the current ask) and, when both exist, **"$40k over / under your max"** (`vs_max_bid`; red when it sold above what the buyer would have paid, green below) — the comparison that tells a buyer whether their bidding instincts were right. An outlined **✕ Remove** button (red on hover) drops the home from the list and from Watchlist alerts (09 §2) — `PATCH /api/watchlist/:property_id {watching: false}`; its tours and tracker row are kept, and `👁 Watch` on the detail page puts it back.
- Dates are rendered as local calendar days (`YYYY-MM-DD` parsed as a local date, not UTC midnight).

## 6. Compare (`/compare?ids=`)
Side-by-side columns (2–4 tracked listings): photo, list price, CMA estimate, predicted range, $/sqft, PITI at p50, CDOM, hazard chips, sqft mismatch, disclosure status, my max bid. Rows highlight best value per row.

## 7. Affordability (`/affordability`)
Three cards, answer first, every field in plain words with a one-line hint:
- **What can I afford?** (full width, top): the profile-only `/offer/solve` answer as one big number "in {city}" and its plain-language verdict naming the binding limit — **only once an income is entered**; without one (`limits.payment` null) the card says "Enter your yearly income below to see what you can afford" instead of a number or the limit rows, since cash and the 20% floor alone ignore the monthly payment. With an income, the three limits as rows — *Monthly payment lenders allow on your income* (or "add your income below"), *Your down payment as 20% of the price*, *Cash for down payment, closing costs and a 6-month reserve* — each "up to $X", the binding one bold; "The lowest of the three is what you can afford."
- **Your numbers** → `PUT /api/profile`, saved on blur: down payment and **other savings** (left after the down payment, for closing costs and a cushion) — two amounts that never overlap; the profile stores their sum as `cash_available`, and changing the down payment keeps the other savings as they are — then yearly income (before tax, everyone on the loan), other monthly debts, interest rate (blank = today's rate, shown as the placeholder), home insurance per month, the pack's optional-peril toggle (earthquake under `ca`, labelled from `GET /api/config`). **Advanced** (collapsed): *Extra above the appraisal (%)* — the appraisal-gap tolerance, entered as a percent, used by per-listing bid advice.
- **Check a price**: price, city (sets the tax rate; the geography's cities, first one default; also the city of the answer above), HOA per month → monthly payment, a ✓/⚠ line against the income payment limit, the labelled breakdown (mortgage, property tax, insurance, earthquake, PMI, HOA; zero lines hidden), the rate and tax rate used, cash needed (down + closing), the 6-month reserves line, and the pack's reassessment / supplemental-tax note.

## 9. Supply (`/supply`)
Everything months-of-supply, from `/api/market/supply?window=` (07 §Market). Nav position is between Alerts and Data Log. **The live series is the default everywhere**: it leads the focus panel and the table, is the table's default sort, and is the trend charts' default metric — Redfin's published series is the history and context beside it.
- **Section order**: explainer, then a control bar, then the focus-ZIP panel, then the two trend charts, then the ZIP comparison table, the city context table, and the definitions last — the charts sit above the 25-row table so they are seen without scrolling past it.
- **Control bar**: one card holding the **live-window picker** — a labelled segmented button group (`3 months | 6 months | 9 months | 12 months`, default 3, with the one-line hint "closed sales counted behind every live figure") — and, right-aligned, the as-of readout. The picker drives the live column, the focus panel's live value, both trend charts (when their metric is the live series; they re-query `/series` with `period=<n>m`) and the definitions. One picker for the whole page, never one per section. The choice lives in the URL as `?window=6` (default omitted) so a view can be linked and survives a reload.
- **Explainer strip**: what MOS is, that `Live` is our own daily-scan now-cast over the picked window while `Redfin` is the published rolling 3-month figure that trails by about a month but carries years of history, and that the bands are peninsula-calibrated rather than national — so *vs own 3y* is usually the more useful column (06 §9).
- **As-of readout** (in the control bar): `Live as of 2026-09-26` and `Redfin window 2026-06-01 → 2026-08-31` (`period_start` → `window_end`). Non-negotiable: the Redfin series is stamped by window *start*, so without this it reads as stale.
- **Focus-ZIP panel**: ZIP picker (`94402 — San Mateo`); large `Live (n mo)` value first, then `Redfin`, band chip, 90-day delta, and a plain-language sentence placing the ZIP's Redfin figure in its own three-year range ("tighter than usual, expect competition" / "looser than usual" / "about normal").
- **ZIP comparison table**: all target ZIPs — ZIP, city, live (window in the header), Redfin, 90d, vs own 3y, band. Sortable, default sort live descending; row click → filtered Listings page.
- **Trend charts**: two stacked `/api/market/series` line charts, **up to 8 geos** each over 3 years, sharing one metric picker set (months supply live — labelled with the picked window — / months supply Redfin / inventory / homes sold), default the live series — **Trend — ZIP** then **Trend — city** beneath it. (The Dashboard's own explorer, §1, stays at 4.) **A ZIP is always shown with its city** — picker pills, legend and tooltip read `94402 · San Mateo`; the city chart's pills are the city names. Series colours come from the fixed 8-slot categorical palette in `frontend/src/lib/chartColors.ts`, validated against the white chart surface for colour-vision deficiency. Two binding rules: assign slots **in fixed order, never cycled** — the 9th series is not a generated hue, the picker disables further selection instead; and **colour follows the entity, not its rank** — a slot is held by the series occupying it, so deselecting one series must never repaint the others (implemented as a positional slot array with nulls for freed slots). Three slots sit under 3:1 contrast on white, so the legend is mandatory and identity is never colour-alone; selected picker pills carry a matching colour dot. The live series carries a one-line note that its history begins with the app's first scan (July 2026) with daily points for every window (05 §3.5 backfill). A series shorter than three points is drawn with dots, since a line alone would be invisible. ZIP and city Redfin series are both rolling 3-month windows labelled by window start, so the two charts line up period for period and need no reconciliation note.
- **"What these metrics mean"**: definition list for the four picker metrics, live first — months supply live (own-scan now-cast: active now ÷ closed sales in the picked window ÷ months; no lag; 3 months reacts fastest, 12 smooths seasonality; counts only scanned homes), months supply Redfin (Redfin's ratio; ZIP and city both rolling 3-month windows labelled by start, so the newest point ends about a month ago; the series with years of history that band / 90d / vs own 3y describe), inventory (the numerator; a last-day snapshot, never accumulated across a window), homes sold (the denominator's input; a 3-month total on ZIP and city rows). Must state that falling sales raise months supply exactly as much as new listings do, so the two are read together.
- **City context table**: the same two figures rolled up to the city — the values a thin ZIP borrows.
- A value borrowed from the parent city (`*_basis === 'derived_city'`) **must** carry a `city` badge wherever it appears, here and on the Dashboard tile. Rising supply is shown green (more choice for a buyer), falling red.
- Empty state: "No supply data yet — run `hb pipeline market-supply` to fill this page."

## 11. Field (`/field?ids=a,b,c`) — tour capture, one home at a time (docs/13 §11)
The tour checklist (`hb.tour_spec`, the same spec as the tour panel of §3 item 6c) laid out to be held in one hand while walking a house: the day's homes picked once, then one home at a time through four big-button screens. It is an ordinary page of the SPA, opened in any browser that reaches the app — on the LAN, or anywhere over Tailscale with the home-server setup (`docs/16` §5); nothing is installed.

**Three entries.**
- **Bare `/field` with a set remembered on this device** — `<Navigate replace>` into `/field?ids=<that set>` (`hb.field.set.v1`, written whenever capture mounts), so a bookmark or a reload lands back in the tour instead of the picker. `?pick=true` — the sidebar's Field item, Get Ready's Field link, the capture screen's **Change homes** — bypasses the resume.
- **`?pick=true`, or bare `/field` with nothing remembered — home picker.** The default list is only what the buyer already said they care about — **homes on the Tracker and homes on the open-house schedule** — never a wall of every active listing. Rows are grouped under **Picked** (every ticked home, whatever the search says, so a home picked from a search result survives clearing it), **On your open-house schedule** (soonest slot first; one `open house Sat 1 PM` chip per live slot, read from the same `["open-house-schedule"]` query Open Houses and the boot prefetch use) and **On your tracker** (tracker order, stage chip); a home that is both shows both chips. A **search box** (address, city, ZIP; 250 ms debounce) filters those groups client-side with the server's every-token rule and, while non-empty, adds a **More listings** group from `GET /api/listings?q=…&status=active` (50 rows) for anything not already on the list. **✕** on a schedule/tracker row removes the home **at the source** — `DELETE /api/tracker/{id}` and/or `DELETE /api/open-houses/{id}/schedule` for each of its slots, the same ✕ those pages carry, no confirm — so it leaves the list on every device; search hits have no ✕. When a set is remembered, an **"N homes in progress"** card (addresses from `hb.field.homes.v1`) sits above the list with **Continue** and **Clear**. Clear first saves anything outstanding (the same save as capture) and only then forgets the set and drops those homes' stored seed and answers, so an unsaved answer is never lost — if the save fails, nothing is cleared and the card says so. With no connection an amber notice says only the homes already loaded are usable. "Start field mode" links to `/field?ids=…`.
- **"How to use Field mode"**, a `<details>` panel open by default (its collapse is remembered per browser in `hb.field.help.v1`): four steps — pick the homes (Tracker + schedule, search for the rest); at the house, the address menu switches homes and the four screens are walked in order, every tap saved; afterwards each visit is on the listing's Tour log and the Tracker; "Change homes" / sidebar Field returns to the picker, **Clear** empties the in-progress set, and ✕ removes at the source. On-screen copy names no device and no technical term (no "phone", "server", "JSON").
- **With `ids` — capture.** Writes the set to `hb.field.set.v1`, seeds once from `GET /api/tours/field-data` into `localStorage`, then renders from `localStorage`. A home whose seed could not load shows a "couldn't load" state (with a **Change homes** link).

**Four grouped screens per home**, following the playbook walk (docs/13): **Outside** (Street + Exterior) → **Systems** → **Inside** (Interior + Life) → **Agent & verdict** (Agent Q&A + Verdict). Each screen stacks its constituent sections under sub-headings, so related items are one scroll rather than a Next tap (the seven walk sections, aggregated 2/1/2/2). Sticky header: back, the address as a native `<select>` (**HomeSwitcher** — every home of the set plus **Change homes…**, so jumping between homes is one tap and the iOS wheel picker), `n/4`, progress dots (plus `Home k/N` when multiple). Sticky footer: the running deferred-maintenance range + **Next / Next home / Finish**. Context notes show as an amber banner on the first screen.

**Thumb-first inputs** (fewest taps with a gloved thumb): `choice` with ≤4 short options → one-tap **segmented pills**; a longer `choice` (e.g. 9 panel brands) → native `<select>` (iOS wheel picker); `bool` → full-width toggle row; `rating` → five large squares; `number` → `inputMode=numeric`; `text` → textarea; each item's photo shot-list → a checkbox carrying the exact shot text (stored `photo:<key>`). The Verdict screen also carries gut-score, verdict, and notes.

**Live red flags** use the same `isFlagged` interpreter as the tour panel, lifted to `frontend/src/lib/tourFlags.ts` and imported by both; its `rollupFlags` computes the **deduped** deferred-maintenance range on the phone (same dedupe as `tour_spec.evaluate`).

**Saving** (the part that must not lose data). Every edit writes through to `localStorage` **synchronously, no debounce**, so a tab killed the instant after a tap has still kept it, and marks the home pending (`hb.field.pending.v1`). The save follows **1.5 s after the last tap** while online (one save at a time across the page, `saveOutstanding()`; 15 s back-off after a failure), on reconnect, on **Finish**, from **Save now**, and from the picker's **Clear**. A home edited while its requests are in flight stays pending, because what was sent no longer matches what is stored: per home `POST /api/tours` (idempotent on `(property_id, toured_on)`) then `PATCH /api/tours/{id}` with the accumulated state — the phone is authoritative for what it just observed, so PATCH overwrites scalars and merges JSON (deliberately **not** `/import`, which gap-fills and would refuse a correction). A persistent **status bar** is never silent: "Loading k/N homes…" / "N homes loaded" / "Saving…" / "All answers saved ✓" / "N homes not saved yet" with **Save now** / "Save failed — retrying" / "No connection · N answers kept, saved when it's back". **Copy answers** copies the raw `{tours:[…]}` JSON ("show" reveals it) so answers that never saved are never a dead end — that JSON is exactly what `POST /api/tours/import` consumes. Each successful seed also **prunes** `hb.field.homes.v1` / `hb.field.answers.v1` to the current `ids` plus anything still pending — a home loaded on an earlier day and long since saved would otherwise sit on the phone forever (each carries a full spec), and a store that hits the quota makes the write-through silently stop persisting.

**Print.** A `@media print` sheet renders the full checklist per home to paper — the fallback when a phone dies.

- Empty states (picker): nothing tracked or scheduled and no search — “Nothing on your Tracker or open-house schedule yet — search above, or star listings and schedule open houses first.”; a search with no hit anywhere — “No active listings match.”; the search failing — “Search needs a connection — the list below is what's already loaded.”

## 12. Closing (`/closing`) — offer accepted → keys (docs/14)

The page for the half of the process that starts where every other page stops. Backed by
`/api/deals/*`; every date on it is derived by `hb/closing_spec.py` from the deal's five
contract numbers and recomputed on read.

- **Legal banner, always visible**: these dates are arithmetic on numbers the user typed off
  their own contract, not authority — the contract governs; this is not legal advice; with no
  buyer's agent a real estate attorney (the pack supplies the jurisdiction wording, `attorney_phrase`) on a flat fee is the highest-value purchase available.
  It belongs on the page, not only in the doc, because the page is what gets used under time
  pressure.
- **The closing playbook** (`MarkdownGuide`): the pack's guide — docs/14 §1–§14 under `ca` — fetched from `GET /api/guide/closing` and rendered as markdown (react-markdown + remark-gfm) in full on the page —
  one collapsible chapter each (what you lost, forms and agency, days 0–3 with the wire-fraud
  rules, the contingency clock, the disclosure packet, inspections, city point-of-sale rules,
  loan/appraisal/gap, insurance, repairs and credits, removing contingencies, the final week,
  cash to close, week one after close), with every table, cost band and worked timeline. Open
  by default in the empty state, collapsed once a deal exists. Every phase accordion carries
  **"Read the guide:"** links that open and scroll to the chapter it came from, the Estimated
  costs card links to cash to close, and cross-references inside chapters jump between them.
  Nothing on the page sends the user to a markdown file — the page is what gets read. A pack with no guide (the `us` base) shows a one-line note in its place and the guide links are hidden.
- **Clock strip** (the reason the page exists): a chip per anchor — deposit due, investigation,
  appraisal, loan, COE — each showing a day countdown and the resolved date. Amber ≤ 3 days,
  red once negative, and **struck through + "waived"** for a contingency whose day-count is
  NULL.
- **Overdue banner** when anything is past due, naming the blocking items first.
- **Contract card**: acceptance date, COE, purchase price, deposit (`MoneyInput`), the three
  contingency day-counts each with an inline **waive** control (and a restore to the pack's default for that clock), escrow number,
  status. Field-level autosave on blur, house style.
- **Next up**: the earliest unfinished task with its *why*, plus done / overdue / due-soon counts.
- **Estimated costs**: the pack's closing cost-band roll-up, deduped by line, labelled with the
  cost book's year and label ("2026 SF-Peninsula contractor ranges" for the packaged geography)
  as estimates rather than quotes (docs/14 §13).
- **Phase accordions** (`lock_down`, `disclosures`, `inspections`, `loan`, `title_insurance`,
  `negotiate`, `final_week`, `post_close`): one row per task with a checkbox, an owner chip, the
  resolved due date and countdown, a red **BLOCKING** badge, the pack's form code where one
  exists, a cost band where one applies, and an expandable **why / how** body plus a note field.
  Row tints amber when due within 3 days and red when overdue. Phases open by default until
  complete. This is where the playbook's guidance actually reaches the user — attached to a
  dated task rather than sitting in a document nobody re-reads.
- **Deal team**: contacts CRUD, with a standing note that escrow and title are neutral and the
  listing agent represents the seller — and that the escrow officer's direct line lives here
  precisely so wire instructions can be verified against a number that did not come from the
  email carrying them. The roster also lists the contacts saved on the listing's detail page
  before the offer (§3 1c; 04 §contacts) — the same listing agent, now across the table in
  escrow — and remove works on those rows too.
- **Empty state is not empty**: with no deal, the page lists homes at `offered`/`won` to start a
  tracker from, and renders the full task spec read-only from `GET /api/deals/spec` — reading
  the process before a contingency clock is running is the entire point — with the playbook open
  above it.

## 14. Open Houses (`/open-houses`) — find this weekend's open houses, schedule the ones to go to, route each day (05 §4c)
Upcoming open houses for active single-family homes, from `GET /api/open-houses`; the buyer's schedule from `GET /api/open-houses/schedule`; each scheduled day's route from `POST /api/open-houses/route`.
- **Range chips**: This weekend (default — the server's now → end of Sunday window), Today, Next 7 days. Then max distance (any / 2 / 5 / 10 / 15 / 25 mi), city, `min $` / `max $` price inputs (comma-formatted `MoneyInput` boxes that apply as you type), sort (soonest / closest / price), a `hide viewed` checkbox, an `N open houses · M homes · K not yet viewed` count, and — once a home has been opened from this tab — an amber `↩ last opened: <address>` chip that scrolls back to it. Price defaults to the shopping band like Listings (§2): untouched inputs show the band and a dark `band $X–$Y ✕` chip; ✕ clears both, and a typed value replaces the band.
- **Origin line** under the filter bar: `Distances from <address> change`. With no origin set it is an inline form — "Set your home address to see distances and plan routes" — writing `PUT /api/open-houses/origin`; an unresolvable address says so inline. Saving refetches the list, the schedule and its routes.
- **Split view** like §2: the list (left) ↔ the schedule panel above `MapView` (right). The map has one pin per home labelled with its first slot in the window (`Sat 1 PM`, prefixed `✓` when that home has a scheduled slot), plus a pin for every live scheduled home the list's range or filters leave out (labelled with its scheduled slot), and a Home pin; hover syncs both ways without moving the list (a map hover only tints the home's rows; the cursor crossing the map on the way back from a detail tab would otherwise yank the list away). A pin click opens the detail page like a row click and brings that home's first row into view.
- **The list is grouped by day** under sticky dark header bands: the full weekday in bold (`Saturday`), the date (`Oct 17`), an amber `Today` / `Tomorrow` pill when it applies, and on the right `N open houses · M scheduled`. Above the list, when the window spans more than one day, a **jump bar** has one button per day (`Sat Oct 17 / 54 open`, with `Today`/`Tomorrow` in place of the weekday) that scrolls the list to that day. Days always run chronologically; the chosen sort orders rows inside each day. Every time renders in the API's `timezone`, not the device's.
- **Row**: start time (bold green) and `to <end>` (plus "virtual" when the slot has that method), thumbnail, address, `city zip · bd/ba · sqft · N mi`, the source's description (host / blurb, truncated, full text on hover), price + `ListingBadges` (open-house chip hidden), and actions:
  - `Directions ↗` — Google Maps from the origin to the home.
  - `Event link ↗` when the source has one.
  - `+ Schedule` / `✓ Scheduled` (green) — puts the slot on, or takes it off, the schedule (`PUT`/`DELETE /api/open-houses/{id}/schedule`). A scheduled row keeps a green left bar and tint.
  - `Log visit` (only once the slot has started) — `POST /api/tours` with `kind: open_house` and `toured_on` = the slot's local date (idempotent per home and day), then opens the detail page, where the tour log lives (§3).
  - Row click opens the detail page in a new tab, as on Listings.
- **Viewed / last opened**: the §2b unread-mail pattern, keyed on the listing's `viewed_at` (stamped by the first detail-page open, flipped locally on click since the list does not refetch on window focus): unviewed homes carry a blue dot before the address; viewed ones are dimmed with a gray `✓ viewed`. The home opened most recently gets an amber left bar, tint and `last opened` pill instead. `hide viewed` drops viewed homes except those opened during this visit, so the row just clicked never vanishes.
- **Coming back keeps your place**: range, filters, `hide viewed`, the opened-this-tab set, the last-opened home and the list's scroll position are kept in `sessionStorage` (`hb.open-houses.v1`, per browser tab). Leaving for a detail tab saves the scroll position; returning brings the last-opened row into view if it moved off screen; a reload — or a phone discarding the backgrounded tab — restores filters and scroll once the rows load. The list query skips refetch-on-focus so returning never re-sorts it.
- **My schedule panel** (above the map, always shown): the open houses the buyer plans to go to, saved in the DB so it survives reloads and is the same on every device; it is independent of the list's range and filters. Header `My schedule · N open houses · M days`. Then one tab per scheduled day (`Saturday Oct 17 / 4 stops`, defaulting to the first day), and for the chosen day its route **in the buyer's own order** (`schedule_position`; a newly scheduled home goes last): `~N min driving`, then every live stop numbered — `⋮⋮` drag handle, `<address>, <city>` (opens the detail page), `open <window> · N min drive` beneath — with ▲ / ▼ and ✕. Drag a stop onto another (desktop) or use ▲ / ▼ (phone) to rearrange; the new order shows at once and is saved with `PUT /api/open-houses/schedule/order`, then the drive times refresh. **No stop is ever dropped** and there are no arrive/leave times — whether to squeeze in a home that closes early is the buyer's call. `Auto-order for <15 / 20 / 30 / 45> min stays` (default 20; shown with 2+ stops and an origin) asks the planner for the order that fits the most open-house windows with the least driving (`POST /route` with `optimize`) and saves it; homes it can't fit go last, still listed. `Open route in Google Maps ↗` (multi-stop directions, origin first, in this order) covers the first 10 stops, with a note to open the rest from stop 11 when more are scheduled. Below in red: scheduled slots the source cancelled ("open house cancelled (no longer listed)") and ones whose home is no longer active ("home is now pending") — kept out of the route. Every entry has a ✕ that unschedules it. Hovering a stop (route or red line) tints it and turns its map pin red — and tints that home's list rows — the same hover sync as a list row. With no origin set, the day is the same reorderable list without drive times, plus a prompt to set the address. Empty state: "Nothing scheduled yet. Hit + Schedule on an open house you plan to go to — it's saved here, and each day gets a driving route."
- Empty state: "No open houses scheduled in this window — widen the range or filters, or run `hb pipeline open-houses`."
- Rationale: open houses are the one showing a buyer without an agent can walk into unannounced, and most of them run in the same Sat/Sun 1–4 PM window — the hard part is choosing which four fit in an afternoon, which a time-window-aware ordering answers better than a distance sort.

**Offline (read-only).** `main.tsx` wraps the app in `PersistQueryClientProvider` and persists **only** the `open-houses`, `open-house-schedule` and `open-house-route` queries (successful ones) to `localStorage` under `hb.query.v1`, `maxAge` 7 days (the default `gcTime` matches, so restored entries survive until the page mounts), with a manual `buster` bumped when an open-house response shape changes. Offline, TanStack Query's default `networkMode: "online"` pauses the fetches and the restored data renders; back online, stale entries refetch. The route is a `POST` no HTTP cache would hold, which is why the query cache is persisted rather than responses. My schedule is prefetched on every online boot, so it is on the device even when this page was never opened; the slot list and each day's route are saved when viewed — so the pre-load is: open Open Houses (the default "this weekend" view) and each day tab in My schedule once on wifi. There is no service worker, so this only helps a tab that already has the shell loaded (or a browser that still has it cached): the app itself cannot be fetched with the LAN out of reach, thumbnails and map tiles are whatever the browser cached, and writes — scheduling/unscheduling, setting the origin, starting a tour — fail offline.
